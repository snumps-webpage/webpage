# 관리자 스터디·세미나 관리 및 회차 목록 설계

상태: D-000257의 구현 지시에 따라 세부 계약을 구체화하고 구현·로컬 검증. 운영 배포 전 사용자 프리뷰 확인 대기.

## 목표

관리자가 주최자·발표자로 등록되지 않아도 스터디와 세미나의 회차·출석을 관리한다. 스터디 개설 후 회차가 없어도 관리자 활동기록에서 찾아 참가자를 편집하고 회차를 추가할 수 있게 한다.

| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |

## 현재 구조와 신고

신고 경로는 `/admin/studies`의 새 레코드 생성이다. 신고 대상 스터디명은 미확인이다.

- `src/lib/server/services/records-admin.ts`의 `createStudy`는 studies에 기록한다. 활동은 회차 생성 시 만들어진다.
- `/study/[id]/manage`와 `/study/[id]/attendance`는 `ensureOrganizer`를 사용한다. 관리자 우회는 없다.
- 관리자 참가자 직접 편집은 현재 작업 브랜치에 구현되어 있고, 조회 당시 원격 main에는 없었다.
- `seminars`의 한 행은 현재 하나의 일정·공개 상태·발표자·자료·활동 연결을 가진다. 공개 시 활동 및 출석 이벤트를 만든다.
- 세미나 일정·공개·취소는 `/admin/seminars`, 발표자 출석 관리는 `/events/manage`에 있다.

운영 조회 및 관련 테스트 결과는 프로젝트 `.tmp/todo.md`에 기록했다. 기존 작업 브랜치 테스트의 통과는 새 구조의 구현·검증 완료를 의미하지 않는다.

## 구조: 기존 세미나 행을 회차로 유지

상위 묶음을 추가하는 구조는 D-000256으로 확정했다. 화면·저장 계약은 D-000257의 구현 지시를 받아 기존 코드 관례로 구체화했다.

상위 세미나 묶음을 추가하고, 기존 seminars 행을 회차로 사용한다. 기존 행의 id·활동·이벤트·신청 명단·자료·공개 및 공지 상태를 유지해 기존 링크와 기록의 이동을 줄인다. 한 상위 세미나에 여러 seminars 행을 연결하면 회차별 운영도 독립적으로 유지할 수 있다.

`seminar-series` 상위 항목은 `id`, 공통 `title`, `description`을 소유한다. 발표자·일정·자료·영상·공개·공지는 기존 `seminars` 회차가 소유하고, `seriesId`와 양의 정수 `sessionNo`로 연결한다. 회차 번호는 상위 항목의 기존 최대 번호 다음으로 DB 잠금 안에서 부여한다. 취소된 번호도 재사용하지 않는다. 기존 저장값은 길이·공백을 보존하고 새 공통 정보 입력에만 제목 trim/300자, 소개 20000자 제한을 적용한다.

대안은 seminars를 상위 항목으로 바꾸고 별도 회차 저장 구조를 만드는 것이다. 개념과 저장 이름은 맞지만 기존 단일 회차를 전제한 서비스·SQL·주소·활동 연결을 옮길 범위가 커진다. 어느 안이든 기존 ID 연결 보존을 검증해야 한다.

### 관리자 화면

| 진입점                       | 제안 동작                                             |
| ---------------------------- | ----------------------------------------------------- |
| `/admin/studies`             | 각 스터디에서 상세 관리로 이동                        |
| `/admin/studies/[id]`        | 참가자 편집·주최자 변경·회차 생성·수정·취소·출석 관리 |
| `/admin/seminars`            | 상위 세미나와 회차별 관리로 진입                      |
| `/admin/seminar-series/[id]` | 회차 추가·발표자·일정·공개·공지 상태·출석 관리        |
| `/admin/activities`          | 확정된 스터디 묶음 표시와 기존 기타 활동 관리         |

스터디 상세 URL은 `/admin/studies/[id]`, 세미나 상위 목록·상세 URL은 `/admin/seminar-series`와 `/admin/seminar-series/[id]`이다. 세미나 상세에서 회차를 만들고 출석을 편집하며 기존 회차별 일정·공개·발표자·자료 관리 화면으로 연결한다.

활동기록의 묶음 표시 대상은 스터디다. 세미나 활동은 기존 목록에서 회차별로 유지한다. 스터디의 실제 회차는 events의 studyId/activityId로 판정하고 이주된 연결 활동은 별도로 표시한다. 검색으로 회차가 숨겨진 경우와 원래 회차가 없는 경우의 안내를 구분한다.

### 권한과 저장 경계

관리자 상세는 관리자 인증을 거친 load와 action으로 구현한다. 일반 주최자·발표자 경로에 일괄 관리자 우회를 추가하는 방식은 제안하지 않는다. 관리자 변경의 행위자는 실제 로그인 관리자여야 하며 주최자·발표자로 대리 기록하지 않는다.

관리자의 종료·취소 스터디 회차 변경은 서버뿐 아니라 DB flow의 상태 검사도 구분해야 한다. 클라이언트가 보낸 관리자 표시만으로 제한을 해제하지 않는다. 회차 수정 시 이벤트와 활동의 제목·일정을 함께 맞추고 기존 출석을 보존한다.

스터디 회차 쓰기는 `flow_admin_study_session`이 studyId·eventId 연결, 실제 actorId, operation을 판정하고 같은 transaction에서 감사 기록을 남긴다. 세미나 쓰기는 `flow_admin_seminar_series`가 상위·회차 소속과 actorMemberId를 판정하고 감사 기록을 남긴다. 스터디 출석 저장은 참가자 범위만 갱신해 현장 출석을 보존한다. 세미나 출석은 관리자가 확인한 해당 회차 명단으로 교체하며 저장된 legacy id를 보존한다. 기존 세미나 발표자 권한은 유지한다.

### 상태와 오류

| 대상                  | 전이·제약                                                                                              |
| --------------------- | ------------------------------------------------------------------------------------------------------ |
| 세미나 회차           | 현행 unscheduled → scheduled → published, 취소는 cancelled 유지                                        |
| 스터디 상위           | 관리자 회차 변경으로 finished·cancelled 상태를 자동 변경하지 않음                                      |
| 스터디 회차           | 관리자는 종료·취소 상위의 회차를 변경 가능. 이미 취소한 회차 자체의 재활성화·출석 변경은 기존대로 거절 |
| 없는 대상·잘못된 연결 | 저장 없이 오류 표시                                                                                    |
| 메일 실패             | 공개 성공과 메일 실패를 구분하고 기존 재시도·중복 방지 계약 유지                                       |
| 동시 회차 생성        | 같은 번호·이벤트·활동의 중복 생성 방지                                                                 |

종료된 스터디도 관리자에게 회차 변경 경로가 생기지만, 일반 주최자 화면의 종료 상태는 그대로 제한된다. 공개·취소 등의 동시 요청은 현재 DB 상태에서 다시 판정해야 한다.

## 데이터 전환

기존 세미나마다 상위 항목 하나를 만들고 기존 행을 첫 회차로 연결한다. 일정 미정·비공개·취소 상태를 유지한다. 활동·이벤트가 없는 기존 기록에 출석 이벤트나 공지 발송을 임의로 추가하지 않는다.

전환 재실행 시 상위 항목이나 회차를 중복 생성하지 않아야 한다. 기존 공개 상세 주소·출석 링크·자료 주소·출석자·신청자·공지 시각과 연결 ID가 전환 전후 동일한지 비교한다. 기존 기록을 묶는 운영 도구와 병합 실행은 이번 제안 범위에 포함하지 않는다.

새 migration은 `20261103000000_admin_study_sessions.sql`과 `20261103000100_seminar_series.sql`이다. 기존 세미나 생성과 신청 승인은 상위 연결까지 같은 transaction에서 수행한다. 구버전 writer가 같은 세미나 문서를 저장할 때 새 연결 필드를 생략하더라도 trigger가 저장된 seriesId/sessionNo를 유지한다. 상위 연결 백필은 재실행 가능하며 배포 직후와 지연 재확인의 기존 절차에 포함한다.

### 실패와 권한 점검

| 진입점·실패                         | 영향                         | 감지·처리                                                                       |
| ----------------------------------- | ---------------------------- | ------------------------------------------------------------------------------- |
| 비관리자의 관리자 action·actor 위조 | 권한 밖 회차·출석 변경       | session actor 사용, DB members 재검사, PUBLIC·anon·authenticated 함수 실행 회수 |
| 다른 스터디·상위의 회차 ID 제출     | 다른 회차 변경               | study/series/event/activity 연결 검사, 저장 없이 거절                           |
| 구버전 writer의 필드 제거           | 회차 묶음 연결 손실          | 같은 행의 기존 metadata 보존 trigger 및 재실행 백필                             |
| 동시 회차 생성                      | 번호·활동 중복               | 정렬된 DB 잠금, transaction, 반복 생성·회차 번호 검사                           |
| 공지 실패                           | 공개 상태와 발송 결과 불일치 | 기존 공지 선점·실패 응답·재발송 정책 유지                                       |

이 표는 확인할 실패 경로이며 가능한 모든 위협을 열거했다는 주장은 아니다. 네트워크·운영 권한은 로컬 PGlite 시험만으로 확인할 수 없다.

## 테스트 전략과 성공 기준

구현 계획에서 테스트 파일과 실행 범위를 확정한다. 최소 검증 대상은 다음과 같다.

- 관리자는 주최자가 아닌 스터디의 참가자·회차·출석 관리 가능. 비관리자는 관리자 action에 접근 불가.
- 관리자는 종료·취소 스터디 회차 변경 가능. 주최자는 기존대로 거절.
- 회차가 없는 스터디도 활동기록에서 검색·표시되고 관리 화면으로 이동 가능.
- 스터디 상위에 참가자 수·회차 수·관리 버튼을 표시하고, 펼치면 해당 스터디의 회차 목록 표시.
- 스터디 상위 표시만으로 활동·출석 데이터와 활동 실적이 증가하지 않음.
- 한 세미나의 두 회차는 발표자·일정·신청자·출석·공개·공지 상태가 서로 독립.
- 세미나 실적은 회차 기준이며 상위 항목으로 중복 증가하지 않음.
- 기존 세미나 전환 전후 링크·자료·신청·출석 및 공지 이력 보존, 재실행 멱등.
- 회차 생성 경쟁·취소 경쟁·잘못된 상위 ID·없는 회차·메일 실패 경계 검증.
- 관련 단위·PGlite 테스트, 타입·lint·빌드 후 실제 브라우저에서 관리자와 주최자 동선 확인.

새 테스트는 구현 전에 실패를 확인한다. 이 문서만으로 수정·구현 완료를 주장하지 않는다.

## 프로젝트 구조와 코드 스타일

기존 `src/routes/(admin)/admin`, `src/lib/components/admin`, `src/lib/server/services`, `src/lib/server/data/schemas`, `supabase/migrations` 아래에 변경을 둔다. 공유 UI는 표시 로직을 재사용하되 권한 판정은 서버가 소유한다.

기존 관리자 action의 형태를 따른다.

```ts
return handleAdminAction(locals, async () => {
  await setStudyParticipants(
    data.get("id") as string,
    (data.getAll("participantIds") as string[]).filter(Boolean),
    locals.member!.memberId,
  );
  return { operation: "studyParticipantsSet" };
});
```

## 경계

- Always: 실제 관리자 인증, 기존 연결 보존, 회차별 활동 인정, 오류와 부분 성공 구분.
- Ask first: 구현 후 사용자 실로그인·프리뷰 확인. 운영 배포는 D-000257의 조건부 승인에 따라 그 확인 뒤 진행. 기존 기록 병합은 별도 확인.
- Never: 상위 항목을 실제 참석 활동으로 중복 생성, 신고 대상을 임의로 특정, 관리자 편의를 위해 일반 회원의 권한 확대, 기존 출석·자료 삭제.

## 남은 운영 확인

dev DB 일시정지 복구와 새 migration 적용, 새 프리뷰에서 기존 D-000246·248의 실로그인·세미나 흐름·회원/관리자 화면 및 새 회차 관리 동선을 사용자에게 확인받는다. 배포 실행 주체는 후속 D-000257을 따른다. 기록 병합·첫 일괄 승급·실제 승인 일시 보정은 기존 별도 확인 절차를 유지한다.
