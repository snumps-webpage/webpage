## 3. 확정된 제품 방향과 기술 계약

### 3-1. 세미나: 승인과 일정 공개 분리

신청 하나는 단발 발표 하나다. “정기 세미나”는 반복되는 하나의 세미나 엔티티가 아니라, 운영진이
학기 초에 받은 여러 단발 발표를 화요일·수요일 같은 정기 슬롯에 배치해 운영하는 방식이다. 따라서
별도의 반복 일정이나 세미나 시리즈 엔티티를 만들 필요는 없다.

정기/비정기 구분은 운영 메모가 아니라 데이터로 저장한다. 신청자가 신청 시 필수 `kind`를 선택하고,
관리자는 승인 전에 이를 정정할 수 있다. 승인 시 같은 값을 생성된 세미나에 복사한다.

```ts
type SeminarKind = "regular" | "irregular";
```

신청자는 제목·설명·선수지식·소요시간·진행자를 제출하되 날짜를 입력하지 않는다. 관리자 승인은
“이 주제의 세미나를 열기로 결정했다”는 뜻이다. 이때 출석 이벤트도 열지 않고 **전 회원 공지도
보내지 않는다** — 날짜 없는 개설 공지는 회원에게 아무 행동도 요구하지 않으면서, 정작 날짜가
정해졌을 때의 공지와 구분되지 않는다. 승인 알림은 신청자 본인에게만 간다.

최소 수명주기는 다음과 같다.

1. 회원이 날짜 없이 세미나를 신청한다.
2. 관리자가 승인 또는 거절한다.
3. 승인된 세미나는 **일정 미정** 상태로 생성되고, 신청자 본인에게만 승인 알림이 간다.
4. 관리자와 연사가 카카오톡 등 운영 채널로 날짜·시간·장소를 조율한다.
5. 관리자가 일정을 저장한 뒤 공개한다.
6. 공개 시 출석 이벤트를 활성화하고 전 회원에게 확정 일정 안내 메일을 보낸다.
7. 공개 후 일정 변경 시 세미나·활동·출석 이벤트를 한 작업으로 갱신하고 변경 전·후 일정을
   안내한다. 공개 세미나 취소 시에도 취소 메일을 보낸다.

따라서 [`FUNCTIONAL-SPEC.md`의 ADM-02](./FUNCTIONAL-SPEC.md#6-1-승인-흐름--현행)와
[`API-SPEC.md`의 `approveSeminar`](./API-SPEC.md#7-2-admin-액션)은 현재의
“승인 즉시 activity + active event + 공지”를 “승인 즉시 일정 미정 seminar + 공지”로 바꿔야 한다.

### 3-2. 스터디: 수동 회차 중심

스터디는 달력상의 반복 일정이 아니라 활동 단위로 기록한다. 출석 체크가 필요한 순간 주최자가
`회차 생성`을 누르면 서버가 입력 폼 없이 다음 회차를 만들고, 그 회차에 출석 링크와 출석부를 연결한다.

- `studies.schedule[]` 제거
- `registerSchedule` 제거
- 크론의 스터디 회차 자동 생성 제거
- `createSession`, `updateSession`, `cancelSession` 유지
- `createSession`에 사용자가 입력해야 하는 필드는 없음. 중복 제출 방지용 숨은 `operationId`만 전송
- `sessionNo`는 해당 스터디에서 서버가 순차 부여
- 제목은 `${sessionNo}회차`, 시작 시각은 서버의 현재 KST 시각으로 자동 설정
- 생성 직후 event는 `active`이며 출석 링크를 바로 표시
- 회차 하나는 activity 하나와 attendance event 하나를 만든다
- 스터디가 `finished`이면 새 회차 생성 불가

이는 기능 명세의 “수동 + 사전 일정 자동 생성 병행”([STU-06](./FUNCTIONAL-SPEC.md#5-발표자주최자-영역--pres--stu--sf2신규))과
API/구현 명세의 schedule·크론 부분을 대체한다.

### 3-3. 폼 검증 오류

모든 폼 액션은 동일한 오류 형식을 사용한다.

```ts
type FormFailure = {
  error: "VALIDATION_FAILED" | ErrorCode;
  issues?: Record<string, string>;
  values?: Record<string, unknown>;
};
```

- Zod의 첫 번째 오류를 필드 경로별 문자열로 평탄화한다.
- 특정 필드에 속하지 않는 오류는 `_form` 키를 사용한다.
- `issues`와 정규화한 `values`는 `VALIDATION_FAILED`일 때만 반환한다.
- 서버 내부 오류, 권한 오류, 존재 은폐 응답에는 입력값·스택·내부 세부사항을 포함하지 않는다.
- 프론트엔드는 입력 아래 필드 오류와 폼 상단 `_form` 오류를 함께 표시하고, 첫 오류 필드로 포커스를 이동한다.

### 3-4. 파일 업로드

기존 의존성과 구현 명세의 S3 presigned PUT 방식을 유지하되 wire contract를 다음으로 고정한다.

```ts
type PresignRequest = {
  operationId: string;
  purpose: UploadPurpose;
  filename: string;
  contentType: string;
  size: number;
};

type PresignSuccess = {
  success: true;
  upload: {
    url: string;
    method: "PUT";
    headers: { "Content-Type": string };
    expiresAt: string;
  };
  file: {
    operationId: string;
    s3Key: string;
    purpose: UploadPurpose;
    filename: string;
    contentType: string;
    size: number;
  };
};
```

- 활성 purpose: `seminar-material`, `seminar-photo`, `study-photo`, `gallery-photo`
- 모든 활성 purpose는 관리자만 발급받는다. 세미나 신청 첨부는 이 업로드 경로를 사용하지 않는다.
- 허용 이미지: JPEG, PNG, WebP, 최대 10 MB
- 문서: PDF, 최대 50 MB
- URL 유효기간: 10분
- 브라우저는 같은 키에 대한 네트워크 오류/5xx PUT을 최대 2회 자동 재시도한다. 4xx는 재시도하지 않고 새 presign을 요청한다.
- 업로드 성공만으로 레코드에 연결하지 않는다. 이어지는 폼 액션이 `operationId`와 `s3Key`를 등록한다.
- 서버는 key의 purpose·발급 사용자·만료·미등록 여부를 검증한 뒤 pending key를 정식 key로 이동한다.
- 등록 액션은 같은 `operationId`의 재전송에 멱등이어야 한다. 미등록 key는 7일 후 삭제한다.

### 3-5. 관리자 폴링

세 관리자 큐 엔드포인트는 같은 봉투를 사용한다.

```ts
type QueueResponse<T> = {
  success: true;
  items: T[];
  generatedAt: string;
};
```

- `GET /api/admin/applications`
- `GET /api/admin/seminar-requests`
- `GET /api/admin/study-requests`
- 정렬: 오래된 pending 요청 우선
- 주기: 관리자 화면이 보일 때만 30초
- 탭이 숨겨졌거나 브라우저가 offline이면 중지
- 다시 보이거나 online이 되면 즉시 한 번 재검증
- 승인·거절 성공 후 타이머를 기다리지 않고 해당 큐를 즉시 재검증
- 응답 오류는 공통 REST 오류 `{ error }`를 사용하며, 직전 성공 목록을 지우지 않고 새로고침 실패 상태를 표시

### 3-6. 로그인 복귀 URL

- 쿼리 이름은 전 구간에서 `redirectTo`만 사용한다.
- 값은 같은 origin의 `/`로 시작하는 상대 경로만 허용한다.
- `//`, scheme 포함 URL, 역슬래시, 제어문자가 포함된 값은 `/`로 대체한다.
- 로그인 시작 → OAuth callback → 승인/대기 가드를 거치는 동안 안전한 `redirectTo`를 보존한다.
- 기존 `redirect` 파라미터의 호환 계층은 만들지 않고 호출부를 일괄 교체한다.

### 3-7. 승인/생성 멱등성

현재 구현 명세의 `` `${studyId}:${date}` ``는 ULID가 아니며, 새 수동 회차 모델에서는 날짜가 고유하지도
않다. 다음 두 개념을 분리한다.

- `sourceRequestId: ULID | null`: 세미나/스터디/가입 신청처럼 실제 원본 신청 레코드가 있을 때만 그 ID를 저장
- `operationId: UUIDv7`: 사용자가 시작한 다중 테이블 쓰기의 재전송을 식별하는 별도 키

세미나 승인·스터디 승인은 원 신청 ID로 check-before-create한다. 수동 스터디 회차 생성, 업로드 등록처럼
원 신청이 없는 작업은 클라이언트가 생성한 `operationId`를 폼과 함께 보내고 서버가 작업 결과에 기록한다.
같은 키와 같은 입력은 기존 결과를 반환하고, 같은 키에 다른 입력은 `CONFLICT`를 반환한다. 복합 문자열을
`sourceRequestId`에 넣지 않는다.

## 4. 백엔드 명세에 요구할 변경

### 4-1. 페이지 DTO를 명시하는 방식

각 페이지 load는 테이블 원본을 그대로 반환하지 않고, API 명세에 이름 붙은 DTO와 필드 목록을 적는다.
폼 액션도 입력·성공·실패 DTO를 모두 적는다. 최소한 다음 계약이 필요하다.

| 화면/기능                              | 백엔드가 명시할 DTO                                                                    |
| -------------------------------------- | -------------------------------------------------------------------------------------- |
| `/` 게스트                             | `LandingPageData`: 소개, 현재 회장단의 공개 가능한 필드만                              |
| `/` 회원                               | `MemberDashboardData`: 내 프로필 요약, 학기별 활동, 신청 상태, 대기 출석               |
| `/seminar/apply`, `/seminar/edit/[id]` | `MemberPickerItem[]`, 신청 초기값, 권한 플래그, 필드 오류                              |
| 승인 후 세미나 관리                    | `SeminarSchedulingData`: 신청 내용, 발표자, 일정 상태, event 연결 상태, 공개 가능 액션 |
| `/study`, `/study/[id]`                | 목록/상세 DTO, 내 참여 상태, 허용 액션                                                 |
| `/study/[id]/manage`                   | 참여 대기, 참여자, 수동 회차 목록, 전달 상태, 허용 액션. 반복 schedule은 없음          |
| `/admin` 및 큐                         | 큐 item DTO, 개수, 허용 액션, 마지막 갱신 시각                                         |
| 공개 회원/임원                         | PII가 제거된 `PublicMember`, 동의가 확인된 연락처만 포함하는 `PublicExecutive`         |

DTO는 사용자가 수행 가능한 액션을 `canEdit`, `canPublish` 같은 서버 계산 boolean으로 제공해도 되지만,
인가의 근거는 항상 서버 가드와 최신 레코드 재조회다. 프론트엔드의 boolean은 표시 제어일 뿐 보안 경계가 아니다.

### 4-2. 세미나 백엔드 변경

`seminar-requests.status`는 신청 심사 상태(`pending | approved | rejected | withdrawn`)만 표현한다. 승인 후
생성되는 `seminars`에는 별도의 일정/공개 상태가 필요하다.

```ts
type SeminarPublicationStatus =
  "unscheduled" | "scheduled" | "published" | "completed" | "cancelled";

type SeminarSchedule = {
  startsAt: string;
  endsAt: string | null;
  location: string;
};
```

- `seminar-requests.kind`: 신청자가 선택한 `regular | irregular` 필수 값
- `seminar-requests.attachmentUrl`: 선택적 `https` 외부 자료 URL. 직접 업로드 key가 아님
- `seminars.kind`: 승인 시 신청에서 복사된 값. 관리자가 정정 가능
- `approveSeminar`: 세미나를 `unscheduled`로 생성하고 신청을 approved로 바꾼다. activity/event도, 전 회원 공지도 만들지 않는다
- `scheduleSeminar`: 날짜·시간·장소 저장, `scheduled`로 전이
- `publishSeminar`: activity + active event를 멱등 생성하고 `published`로 전이한 뒤 확정 일정 공지
- `updateSeminarSchedule`: 공개 전에는 단순 수정. 공개 후에는 연결된 activity/event도 함께 수정하고 변경 전·후 일정 공지
- `cancelSeminar`: 세미나와 연결 이벤트를 `cancelled`로 두고, 이미 공지된 세미나가 아직 열리기 전이면 취소 공지(사실만). 기록은 남기고 회원·게스트 면에서만 사라진다
- 취소 권한: 개설자는 자기 세미나를 **열리기 전까지만**, 관리자는 이후에도 가능하되 두 번째 확인을 거친다. 판정은 캐시가 아니라 쓰기 시점의 행으로 한다
- pending 신청 수정: 신청자 본인 또는 관리자만 가능
- 승인된 세미나의 내용·일정 수정: 관리자만 가능. 발표자용 직접 수정 액션은 만들지 않음

승인·확정 일정·변경·취소 공지 실패는 상태 변경을 롤백하지 않고 기존 `mailFailed` 성공 페이로드
규칙을 따른다. 상태 전이가 없거나 일정 값이 동일한 재요청에는 메일을 보내지 않는다.

### 4-3. 스터디 백엔드 변경

- `studies.schedule` 필드 및 `generatedEventId` 제거
- `registerSchedule` 액션 제거
- `/api/cron/sync-events`에서 스터디 자동 회차 생성과 `generated` 응답 필드 제거
- `createSession` 입력은 숨은 `operationId`만 받으며, 회차 제목과 시작 시각은 서버가 생성
- activity/event를 같은 `operationId`로 멱등 생성하고 `sessionNo`를 서버가 계산
- `updateSession`과 `cancelSession`은 해당 회차 activity/event를 함께 변경

### 4-4. 직책과 공개 연락처

- 회장·부회장 이름을 코드나 정적 콘텐츠에 쓰지 않는다.
- 서버가 `currentTerm()`과 역할 값으로 현재 임원을 찾는다.
- 공개 응답에는 `PublicExecutive`만 반환한다. `private-info`에서는 현 회장·부회장의 전화번호 하나만 쓴다(§6-4).
- 역할 부여·회수와 기존 데이터 백필은 서버 관리자 책임으로 두며, 이주 자체는 이번 프론트엔드 범위에서 제외한다.
- 첫 릴리스에 `/admin/members/[id]`의 역할·관리자 지정 UI를 제공한다.
- 현재 학기의 회장·부회장의 `private-info` 전화번호를 공개한다. 본인은 `hidePublicPhone`으로 거부할 수 있고
  (옵트아웃), 과거 학기·다른 직책·다른 필드(이메일 포함)는 공개하지 않는다(운영자 결정 2026-09-01).
- 관리자가 관리하던 공개 상태(`PublicContact { status: granted | revoked, … }`)와 저장 필드
  `members.publicContact`는 **폐기**했다(결정 #19, 2026-09-28) — 관리자 화면·입력 스키마·파서가 없고, 필드는
  기존 문서·백업 디코드용으로만 남아 아무도 쓰거나 읽지 않는다.

### 4-5. 활동 유형

`activities.type`과 `events.type`은 다음 하나의 닫힌 enum을 공유한다 — `RECORD_ACTIVITY_TYPES`
(`src/lib/constants.ts`)가 단일 원천이고, 저장 스키마(`schemas/common.ts` `ActivityType`)와 입력 스키마가 이것을 쓴다.

```ts
type ActivityType = "세미나" | "스터디" | "회의" | "회식" | "기타";
```

`문제 창작`·`문제 풀이`는 더 넓은 표시 어휘(`ACTIVITY_TYPES`)에만 있고 저장할 수 없다 — 입력하면
`VALIDATION_FAILED`다. 이주 때 `Seminar`는 `세미나`로 통일했다(API-SPEC §9).

## 5. 프론트엔드에 미치는 구조 변경

- 세미나 신청 폼에는 날짜 필드를 두지 않는다.
- 관리자에는 “심사 대기”와 별개인 “승인됨·일정 미정”, “일정 입력됨·미공개” 작업함이 필요하다.
- 세미나 승인 확인은 공지 미리보기를 제공하지 않는다 — 승인은 메일을 보내지 않는다.
- 세미나 발행 화면은 날짜·시작/종료 시각·장소·발행 확인을 한 흐름으로 제공한다.
- 스터디 관리 화면은 캘린더/반복 일정 편집기가 아니라 회차 타임라인과 `새 회차 만들기`를 중심으로 구성한다.
- 회차 생성 직후 공유 가능한 출석 링크와 출석부로 이어지게 한다.
- 역할과 권한은 클라이언트 상수나 이름 비교가 아니라 서버 DTO와 가드 결과로 표시한다.
- 첫 릴리스 관리자 회원 화면에 `setRoles`·`setAdmin` UI를 포함한다.
- 폼 공통 UI는 필드 오류, 폼 오류, 제출 중 상태, 중복 제출 방지를 동일하게 처리한다.

## 6. 남은 질문, 해소 항목과 보류 사항

### 6-1. 정기/비정기 세미나 — 해소

**해소:** 신청 하나는 단발 발표 하나이며 별도 시리즈/반복 엔티티는 없다. 여러 단발 발표를 운영진이
정기 슬롯에 배치한다. 신청과 승인된 세미나 모두 `kind: regular | irregular`를 저장한다.

최종 일정 입력·변경·발행은 관리자만 수행한다. 발표자와의 조율은 카카오톡 등 외부 채널에서 한다.

전 회원 메일은 **공개 시점부터** 시작한다: 최초 공개 시 확정 일시·장소, 공개 후 실제 변경 시
변경 공지, 취소 시 취소 공지(사실만, 사유 없음). 승인·비공개 일정 저장·동일 값 재저장·지난
일정으로의 정정·이미 지난 세미나의 취소에는 보내지 않으며, 최신 일정은 웹페이지에도 항상 함께
반영한다. 예약 발송은 두지 않는다 — 공개가 곧 공지 시점이다.

### 6-2. 활동 유형 — 해소

여기서 “문제 창작/문제 풀이”는 문제 내용이나 문제 유형을 뜻하지 않는다. 회원의 활동 이력을
분류하는 카테고리다. 예를 들어 회원들이 함께 문제를 만든 모임을 `문제 창작`, 함께 문제를 푼
모임을 `문제 풀이` 활동으로 기록하고, 그 활동에 누가 출석했는지를 저장한다.

- 현행 [`src/lib/constants.ts`](../../src/lib/constants.ts)의 `ACTIVITY_TYPES`에 두 값이 있음
- 관리자 이벤트 생성 화면의 활동 종류 선택지로 사용됨
- 회원 대시보드의 학기별 활동·출석 이력에서 유형 배지/필터 값으로 사용됨
- 새 API의 닫힌 enum에는 `세미나 | 스터디 | 회의 | 회식 | 기타`만 있어 두 값을 저장할 수 없음

**현행 코드 (2026-09-28 정정, 결정 #11)**: 이 두 값은 저장 enum에 들어가지 않았다. 저장되는 활동 유형은
`세미나 | 스터디 | 회의 | 회식 | 기타`(`RECORD_ACTIVITY_TYPES`)이고, `문제 창작`·`문제 풀이`는 표시 어휘
(`ACTIVITY_TYPES`)에만 남아 관리자 기록 편집기·이벤트 생성에서 거부된다. 문제 창작 자료는 활동 기록이 아니라
아카이브(`/archive/problems`, PUB-14)에 둔다. 코드가 기준이다.

### 6-3. 역할 관리 UI — 해소

마지막 답변의 “첫 릴리스에 UI를 제공”은 역할 관리 UI를 뜻하는 것으로 해석했다. 첫 릴리스에
`/admin/members/[id]`의 역할·관리자 지정 UI를 제공한다. 회장·부회장 등을 이름으로
하드코딩하지 않고 서버 관리자가 회원별 학기 역할을 지정한다. 모든 변경은 API 명세대로 감사 로그를 남긴다.

### 6-4. 공개 연락처 — 해소 (개정 2026-09-28)

현재 학기 회장·부회장의 `private-info` 전화번호를 공개한다. 본인이 `hidePublicPhone`으로 거부하면
공개하지 않는다(운영자 결정 2026-09-01, `getPublicExecutives`). 공개 연락처의 출처는 이것 하나다.

처음 결정(관리자가 당사자 확인 후 `granted`/`revoked` 상태와 전화·이메일을 저장)은 폐기했다 — 그 값을
어떤 공개 면도 읽지 않게 된 뒤 관리자 UI만 남아 있었다(audit LB16-3). 결정 #19로 관리자 UI·입력 검증·
파서를 걷어냈고, `members.publicContact`는 기존 문서가 디코드되도록 필드만 남는다(폐기 표시, 쓰는 곳 없음).

### 6-5. 스터디 회차 생성 UX — 해소

주최자가 출석 체크가 필요할 때 입력 없는 `회차 생성` 버튼을 누른다. 서버는 다음 `sessionNo`,
`${sessionNo}회차` 제목, 현재 KST 시각을 자동으로 기록하고 active 출석 이벤트를 만든다. 프론트엔드는
생성 직후 출석 링크 복사 버튼과 출석부 진입 버튼을 보여준다.

오입력 정정을 위한 관리자/주최자 수정·취소 액션은 유지하지만 일반 생성 흐름에는 일정·장소·메모
입력을 요구하지 않는다.

### 6-6. 세미나 신청 첨부와 승인 후 편집

“편집”은 다음 두 기능을 구분해야 한다.

1. **승인 전 신청서 수정:** 현행 `/seminar/edit/[id]`에서 pending 신청의 제목·설명·선수지식·소요시간·연사·첨부 URL을 다시 고친다. 새 API 명세도 신청자 본인과 관리자에게 이 기능을 제공한다.
2. **승인 후 세미나 기록 수정:** 현행 회원 대시보드는 해당 세미나의 발표자에게 제목·비고 `수정` 버튼을 보여준다. 그러나 현재 서버 액션은 로그인만 확인하고 해당 발표자인지 재검증하지 않으며, 새 API에는 이에 대응하는 회원 액션이 없다.

편집 정책은 “pending 신청은 신청자 본인이 수정, 승인 후 내용·일정은 관리자만 수정”으로 확정했다.
발표자용 승인 후 직접 수정 액션과 UI는 만들지 않는다.

첨부는 현재와 같이 Google Drive/Dropbox 등의 선택적 외부 URL 입력으로 유지한다. pending 신청자는
다른 신청 내용과 함께 URL을 교체하거나 제거할 수 있다. 직접 파일 업로드는 제공하지 않는다.

### 6-7. 익명화 회원과 활동 이력 — 보류

요청에 따라 지금 결정을 미룬다. 임원진 논의에서는 다음 모순을 해결해야 한다.

- 공개 회원 명단은 이름·학과·가입일·임원 이력을 유지한다고 되어 있다.
- 탈퇴 익명화 규칙은 이름·학과를 활동 이력에 남긴다고 하면서, 다른 부분에서는 회원 레코드의 일부 필드를 null 처리한다.
- 활동의 `attendeeIds`가 익명화 후에도 회원 ID를 참조하면 재식별 가능성이 남는다.

결정할 내용은 (a) 탈퇴 후 이름·학과 공개 여부, (b) 내부 활동 통계 보존 범위, (c) 회원 ID 참조 유지 또는
익명 식별자로 교체 여부, (d) 임원 이력 보존 여부다. 결정 전에는 익명화 DTO와 공개 화면을 확정하지 않는다.

### 6-8. 남은 즉시 결정 사항

없음. 이 문서에서 확인한 프론트엔드·백엔드 계약은 모두 확정되었다.

익명화 규칙은 요청대로 별도 안건으로 보류한다.
