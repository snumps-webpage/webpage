# Atomic multi-document flows — plpgsql + PGlite

> 결정 2026-09-27 (옵션 B): 여러 테이블 문서를 함께 바꾸는 흐름을 Postgres 함수(plpgsql) 한 트랜잭션으로
> 옮기고, 메모리 백엔드를 PGlite(인프로세스 Postgres)로 바꿔 **같은 SQL을 테스트·로컬에서도 실행**한다.
> 목적은 두 가지 — 원자성(부분 실패 제거)과 로직 일원화(같은 흐름의 구현을 한 곳에).

## 1. 왜

저장 모델은 "테이블 하나 = `app_tables` 행 하나(JSONB 문서)"이고, 앱은 Supabase JS(PostgREST)로 문서를
하나씩 읽고 `version` 조건부로 쓴다(`tables.ts`의 `mutate`). PostgREST 요청 하나가 트랜잭션 하나이므로
**여러 문서를 바꾸는 흐름은 원자적이지 않다.** 읽기와 결정, 쓰기가 여러 요청에 걸쳐 있어 그 사이에 다른
커밋이 끼어든다. 실측(2026-09-27, `scripts/measure`)과 감사에서 실제로 재현된 것:

| 흐름                 | 끼어들 때                                    | 결과                       |
| -------------------- | -------------------------------------------- | -------------------------- |
| 세미나 삭제 ↔ 게시   | 게시가 활동·이벤트를 만든 뒤 세미나가 사라짐 | 살아 있는 고아 이벤트      |
| 세미나 삭제 ↔ 취소   | 삭제가 "게시됨"으로 읽고 취소된 행을 지움    | 취소된 세미나 재공개       |
| 이벤트 삭제 ↔ 체크인 | 대기 행 확인 후 체크인이 들어오고 큐째 삭제  | 체크인 조용히 소실         |
| 출석 승인 ↔ 거절     | 두 액션이 활동과 큐를 따로 씀                | 출석 인정과 큐 상태 불일치 |

지금은 앱 쪽에서 상태를 다시 확인해 **거부(WRITE_CONFLICT)** 하는 식으로 막고 있다. 함수로 옮기면 필요한
행을 잠그고 한 트랜잭션에서 끝내므로 충돌·부분 실패 자체가 생기지 않는다.

## 2. 구조

```
route action ─▶ service (TS)                       ─▶ store.rpc(fn, args) ─▶ Postgres function
               · 입력 검증 (domain zod)                  · supabase: PostgREST .rpc()
               · id·시각 생성 (ULID, KST ISO)            · memory:   PGlite  select fn(...)
               · 결과로 캐시 무효화, 메일·파일 정리 ◀──── { touched: [...], ...result }
```

- **SQL 함수가 하는 일**: 필요한 문서 행을 이름 순서로 `FOR UPDATE` 잠금(교착 방지) → 규칙 검사 → 문서 수정·
  `version` 증가 → 감사 로그 삽입(필요한 흐름) → 바뀐 테이블 목록과 결과 반환. 규칙 위반은
  `RAISE EXCEPTION 'CODE'`(`NOT_FOUND`, `CONFLICT`, …)로 알리고, 트랜잭션 전체가 롤백된다.
- **TS가 하는 일**: 입력 검증, id·시각 생성(함수에 인자로 넘김 — SQL이 id를 만들지 않아 TS와 형식이 같다),
  오류 코드를 `AppError`로 변환, 바뀐 테이블의 캐시 무효화, 그리고 **트랜잭션 밖 부수효과**(메일 발송,
  Storage 파일 정리). 메일은 절대 트랜잭션 안에서 보내지 않는다.
- **단일 문서 흐름**은 지금처럼 `mutate`(CAS)로 둔다. 함수로 옮기는 것은 여러 문서를 함께 바꾸는 흐름뿐이다.
- **공용 SQL 헬퍼**: `app_rows(name)`, `app_put(name, rows)`(upsert + version 증가), `app_lock(names[])`,
  큐용 `app_queue_rows/put/delete`, 행 찾기·교체 헬퍼.

## 3. 검증(zod)과 SQL 사이

SQL이 쓴 행은 TS의 쓰기 게이트(zod)를 거치지 않는다. 대신:

1. 함수는 행을 **명시적 필드로** 만든다(스키마의 기본값도 SQL에서 채움).
2. 모든 함수 테스트는 PGlite에서 실행한 뒤 **바뀐 테이블 전체를 zod로 다시 디코드**한다
   (`expectTablesValid`). 스키마와 SQL이 어긋나면 테스트가 깨진다.
3. 입력 값은 호출 전에 TS가 도메인 스키마로 검증한다.

## 4. 백엔드

| `DATA_BACKEND`              | 저장소                              | 함수 호출                |
| --------------------------- | ----------------------------------- | ------------------------ |
| `supabase` (운영·dev)       | Supabase Postgres, PostgREST        | `supabase.rpc(fn, args)` |
| `memory` (테스트·로컬·실측) | PGlite, 같은 마이그레이션 파일 적용 | `select fn($1)`          |

PGlite에는 Supabase의 `storage` 스키마가 없어서, 마이그레이션 전에 `storage.buckets` 대역 테이블만 만든다.
기존 테스트 헬퍼(`__reset`, `__putRawDoc`, `__docs`, 장애 주입)는 이름을 유지하고 비동기로 바뀐다.

## 5. 보안

함수는 `public` 스키마에 두되 `SECURITY INVOKER`, `search_path` 고정, **`PUBLIC`·`anon`·`authenticated`의
실행 권한을 회수**하고 `service_role`에만 부여한다. 테이블 RLS(deny-all)는 그대로이므로, 공개 키로 호출해도
어떤 행도 읽거나 쓸 수 없다.

## 6. 마이그레이션·배포

- 새 마이그레이션 파일만 추가한다(이미 적용된 `20260901000000_documents.sql`은 수정하지 않는다).
- **확장만(expand-only)**: 함수 추가와 데이터 보정(이주 세미나 27건에 `publicationStatus: "published"`를
  명시)은 지금 운영 중인 코드와도 호환된다. 순서는 **마이그레이션 적용 → 코드 배포**.
- 필드 제거 같은 축소(contract) 단계(예: `studies.schedule`)는 새 코드가 배포된 뒤 별도 마이그레이션으로.
- 되돌리기: 옛 코드는 새 함수를 부르지 않으므로 코드만 되돌리면 된다. 데이터 보정은 되돌릴 필요가 없다.

## 7. 옮길 흐름 (위험 순)

1. 세미나 삭제(`retireHiddenActivity` 포함), 취소, 게시, 일정 변경
2. 출석 승인·거절·삭제, 이벤트 삭제
3. 가입 승인(회원·개인정보·등록·신청 삭제), 세미나·스터디 신청 승인
4. 스터디 회차 생성, 탈퇴 신청(+ 감사 로그를 같은 트랜잭션에)
5. 기록 편집기의 삭제(활동·스터디)

각 흐름은 이전 후 TS 구현을 지운다 — 한 흐름의 구현은 한 곳에만 있다.
