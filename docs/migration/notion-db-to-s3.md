## 0. 확정된 결정 (2026-08-23)

> **Notion을 온전히 대체한다. 편집도, 서빙도 전부 옮긴다. 저장소는 AWS S3.**

이 결정이 이전 판의 권고("Notion을 레코드 원본으로 유지")를 대체한다. 아래 계획은 전부
이 전제 위에 다시 쓴 것이다.

함께 확정된 것:

| # | 결정 | 근거 |
|---|---|---|
| D1 | **정적 문서는 레포에 하드코딩해 서빙한다** | 회칙·회장단·홍보문은 변동이 거의 없다. 이걸 위해 매 요청 저장소를 조회하는 건 낭비다. 빌드 타임에 박아 넣고 CDN에서 정적으로 낸다 |
| D2 | **회원 명단은 현재 공개된 범위 그대로 공개 유지** | 이미 231명이 공개돼 있고 동아리가 그렇게 운영해 왔다. 새로 감추지 않는다 |
| D3 | 레코드 저장소는 S3 | §2 |

> **D1의 함의**: 정적 문서는 S3 테이블에 들어가지 않는다. §2의 `tables/*.json`은 **DB 레코드만**
> 담는다. 정적 문서 편집은 레포 커밋이므로 §5-3의 선택지 중 "레포 PR"로 확정 —
> 다만 이건 **"임원진이 PR을 연다"가 합의된 운영 절차**라는 뜻이고, 그 부담을 줄일
> 보조 수단(마크다운 템플릿, 편집 가이드)이 필요하다.
>
> **D2의 함의**: 회원 테이블은 **비공개 버킷에 저장**하되, 공개 페이지가 노출하는 필드는
> 현재 Notion이 노출하던 것과 동일하게 유지한다(이름·학과·가입일·임원 이력).
> `개인 정보`(이메일·전화·배경지식)는 **여전히 비공개**다 — 지금도 공개가 아니다.

**범위가 공개분에 한정되지 않는다.** Notion이 사라지므로 비공개 DB 4개도 전부 옮겨야 한다.

### 짚고 넘어갈 것 — 이건 데이터 이동이 아니라 시스템 신축이다

"Notion을 대체한다"를 분해하면 데이터 이동은 그중 가장 작은 조각이다.

| 지금 Notion이 제공하는 것 | 대체 후 어디서 오는가 | 신축 필요 |
|---|---|---|
| 레코드 저장·내구성 | S3 (버전 관리 + 조건부 쓰기) | 데이터 계층 재작성 |
| **편집 UI** | **앱에 새로 만들어야 함** | 🔴 최대 작업량 |
| **파일 업로드** | **앱에 새로 만들어야 함** | 🔴 |
| 관계(relation) 무결성 | 앱 코드 | 검증 계층 |
| 뷰·필터·정렬 | 앱 코드 | 이미 일부 존재 |
| 변경 이력·복구 | S3 버전 관리 | 설정 |
| 권한 | 앱 인증 (`auth-guards.ts`) | 확장 |

현재 `/admin`은 **승인 흐름만** 커버한다. 회원 정보 수정, 활동 생성, 세미나 기록 편집,
회칙 개정, 사진 업로드 — 전부 지금은 Notion에서 손으로 한다. 그 전부가 앱 기능이 된다.

**S3는 위 표의 첫 줄만 해결한다.** 나머지는 이 프로젝트가 만들어야 하는 것이고,
이주 비용의 대부분이 거기 있다. 이 문서는 그 전부를 다룬다.

**합계 605행 + 미측정 2개 DB.** 자산 90개.

> 🔴 **`NOTION_DB_EVENTS`와 `NOTION_DB_ATTENDANCE_QUEUE`가 `.env`에 없다.** 코드는 참조하는데
> 로컬 설정이 없어 이벤트·출석 기능이 로컬에서 무동작이다. 프로덕션 Vercel 값은 여기서 확인 불가.
> **이주 착수 전 프로덕션 env를 받아 두 DB의 스키마·행 수를 반드시 실측해야 한다.**
> 회식 갤러리도 env가 없어 코드가 접근하지 못한다.

### 1-1. 🔴 정합성 실측 — 고아 PII가 있다

초판은 "240 − 231 = 9 = 가입 신청 9건"이라 적었다. **우연의 일치였고 틀렸다.**
relation을 직접 따라가 재확인한 결과:

```
private-info 240 =  229 (회원 연결됨)  +  11 (미연결)
members      231 =  229 (개인정보 있음) +   2 (개인정보 없음)
applications   9 =  전부 accepted = true
```

미연결 11건을 이메일로 교차 대조 (해시 비교, 원문 미출력):

| 분류 | 건수 | 성격 |
|---|---|---|
| 이메일조차 없는 행 | **5** | 빈 껍데기. 삭제 후보 |
| 이메일 있고, 회원·신청 어디에도 대응 없음 | **5** | 🔴 **주인 없는 개인정보.** 실존 인물의 연락처가 소유자 없이 남아 있다 |
| 이메일 있고, 가입 신청과 대응 | **1** | 신청 9건이 전부 `accepted=true`인데 8건만 회원으로 연결됐다 → **승인 1건이 중간에 실패한 흔적** |

생성일은 2026-03-02 ~ 2026-04-29에 몰려 있고, 신청 건은 2026-08까지 이어진다.
즉 특정 시기에 발생한 문제이며 현재 진행형은 아니다.

**이주 전 처리 방침이 필요하다** (§8-2). 특히 두 번째 분류 5건은
**주인 없는 개인정보를 새 저장소로 그대로 옮기는 것**이므로, 이주는 이걸 정리할 기회다.
반대로 `개인정보 없는 회원 2건`은 연락 수단이 없는 회원이라 별개 확인이 필요하다.

> 이건 이주가 만든 문제가 아니라 **이미 있던 문제를 이주 조사가 드러낸 것**이다.
> 옮기고 나면 찾기 더 어려워진다.

규모 자체는 작다. **605행은 어떤 저장소에도 부담이 아니다.** 난이도는 크기가 아니라
편집 UI·업로드·권한을 새로 만드는 데서 온다.

## 2. S3를 레코드 저장소로 쓰는 설계

S3는 DB가 아니다. 605행 규모에서 성립시키려면 제약을 명시적으로 받아들여야 한다.

### 2-1. 저장 단위 — 테이블당 객체 1개

행당 객체가 아니라 **테이블 전체를 JSON 객체 하나**로 둔다.

```
s3://snumps-data/
├── tables/members.json           231행
├── tables/private-info.json      240행   🔒
├── tables/activities.json         76행
├── tables/seminars.json           25행
├── tables/studies.json            17행
├── tables/applications.json        9행   🔒
├── tables/seminar-requests.json    5행   🔒
├── tables/events.json              ?    🔒
├── tables/attendance-queue.json    ?    🔒
└── tables/gallery-dinner.json      2행
```

근거: 최대 테이블이 240행이다. 통짜 JSON이 수백 KB를 넘지 않는다. 행당 객체로 쪼개면
목록 조회에 LIST + N회 GET이 필요해져 오히려 느리고 비싸다.

**이 선택의 대가**: 한 행을 고쳐도 테이블 전체를 다시 쓴다. §2-2가 이걸 안전하게 만든다.

### 2-2. 🔴 조건부 쓰기 (If-Match) — 이 설계의 핵심

읽고-고치고-쓰는 사이에 남이 썼는지 ETag로 검사한다. S3는 2024-11부터 이걸 지원한다.

```ts
// 개념 코드
async function mutate<T>(table: string, fn: (rows: T[]) => T[]) {
  for (let attempt = 0; attempt < 5; attempt++) {
    const { body, etag } = await getObject(table);          // ETag 확보
    const next = fn(JSON.parse(body));
    try {
      await putObject(table, JSON.stringify(next), { ifMatch: etag });
      return next;                                           // 성공
    } catch (e) {
      if (e.name !== "PreconditionFailed") throw e;
      // 다른 요청이 먼저 썼다 → 다시 읽고 재시도
    }
  }
  throw new Error("WRITE_CONFLICT");
}
```

이게 있어야 하는 이유는 현행 코드가 이미 lost update에 취약하기 때문이다.
`activities.ts`의 `addAttendeeToActivity`는 retrieve → 배열에 추가 → update이고
그 사이에 아무 보호가 없다. **Notion API에는 `If-Match`가 아예 없어서 지금은 고칠 방법도 없다.**
S3로 옮기면서 이 결함을 같이 없앤다.

**모든 쓰기는 예외 없이 `mutate()`를 통과해야 한다.** 직접 PUT을 허용하면 설계가 무너진다.

### 2-3. 한계와 임계값

| 제약 | 605행 규모에서 | 임계값 |
|---|---|---|
| 인덱스 없음 (`getMemberByEmail`이 전량 스캔) | 231행 배열 순회. 무시 가능 | 수천 행 |
| 테이블 간 원자성 없음 | 승인 흐름이 여러 테이블을 쓴다 → §2-4 | — |
| 쓰기 경합 시 재시도 | 실질 동시 편집자 1~2명. 충돌 거의 없음 | 상시 동시 편집 |
| 전체 재작성 비용 | 240행 JSON = 수백 KB. PUT 1회 | 수 MB |
| 쿼리·집계 없음 | 앱에서 필터 | 복잡 리포팅 요구 |

**임계값에 닿으면 그때는 실제 DB로 간다.** 이 설계는 605행짜리 동아리 데이터에 맞춘 것이고,
그 사실을 문서에 남겨 다음 사람이 잘못된 확장을 시도하지 않게 한다.

### 2-4. 테이블 간 원자성이 없다는 뜻

`admin`의 세미나 승인은 지금도 여러 DB를 연달아 쓴다
(`publishEvent` → `createActivityPage` + `createEvent`, `createSeminarInNotion`,
`updateSeminarRequestStatus`). Notion에서도 원자적이지 않았으므로 **새로 생기는 문제는 아니다.**

대응:
- 쓰기 순서를 **되돌릴 수 있는 방향**으로 고정한다 (부수효과가 가장 큰 것을 마지막에)
- 중간 실패 시 재실행이 안전하도록 **멱등**하게 만든다 (같은 승인을 두 번 눌러도 중복 생성 없음)
- 실패를 삼키지 말고 관리자에게 보인다 — 현행 `handleAdminAction`이 이미 그 자리다

### 2-5. 버전 관리 = 변경 이력 + 복구

Notion의 페이지 기록이 사라지는 것을 S3 버전 관리로 대체한다. 이건 선택이 아니라 **필수**다.

- 버킷 버전 관리 **활성화** — 잘못된 쓰기를 이전 버전으로 되돌릴 수 있다
- 수명 주기 규칙으로 오래된 버전 정리 (예: 비현재 버전 90일 후 삭제)
- 실수 삭제 방지: `MFA Delete`까지는 과하지만, 삭제 권한을 배포 역할에서 분리할 것

### 2-6. 캐시

읽기는 기존 인터페이스를 그대로 쓴다. `withCache(key, ttl, fetcher)`의 페처만 바뀐다.

```
기존:  withCache("all_members", ttl, () => getMembersFromNotion())
신규:  withCache("all_members", ttl, () => getTable("members"))
```

쓰기 후 무효화도 이미 `handleUserAction/handleAdminAction`의 `{ invalidate: [...] }` 옵션에
자리가 있다. **S3 GET은 캐시 미스에만 발생한다.**

## 3. 🔴 개인정보 — S3로 옮기면 위험이 커진다

`개인 정보` 240행(이메일·전화·배경지식)과 `가입 신청` 9행이 S3로 간다.
Notion에서는 워크스페이스 권한이 이걸 지키고 있었다. S3에서는 **우리가 지켜야 한다.**

| 통제 | 요구 |
|---|---|
| 버킷 분리 | `snumps-data-private` 를 공개 자산 버킷과 **물리적으로 분리** |
| CloudFront | 비공개 버킷에는 **연결하지 않는다** |
| 퍼블릭 액세스 | 계정 수준 차단 유지 |
| 암호화 | SSE-KMS (SSE-S3보다 키 접근을 별도 통제 가능) |
| 접근 주체 | Vercel 런타임 역할만. 사람은 기본 접근 불가 |
| 로깅 | 서버 액세스 로그 또는 CloudTrail 데이터 이벤트 |
| 앱 계층 | `개인 정보`는 본인 또는 관리자만. 현행 `auth-guards.ts` 확장 |

> **현재 이미 새고 있다** (인벤토리 §5): `+layout.server.ts`가 모든 라우트에서
> `getLatestExecutives()`를 호출하고 그게 `getPrivateInfo()`로 전화번호를 가져와
> 게스트 표지에 렌더한다. **이주 전에 먼저 고칠 것.** 안 고치고 옮기면
> 결함을 새 시스템으로 이식하는 셈이다.

또한 회원 231명 명단의 공개 범위는 [`notion-pages-to-web.md`](./notion-pages-to-web.md) §9-2
결정을 따른다. 저장은 비공개 버킷, 공개 노출은 별개 판단이다.

## 4. 자산 (90개)

### 4-1. 원본의 성질

서명 URL은 접근 경로마다 형태와 수명이 다르다 (인벤토리 §4).
v3 `getSignedFileUrls`는 `file.notion.so/...?expirationTimestamp=`로 수 시간,
렌더 경로는 S3 presigned로 300초. **블록 `source` 23개 중 10개는 서명 없는 URL이라
그대로 받으면 403**이므로 전부 재발급이 필요하다.

결론: **URL을 저장하거나 핫링크하지 말고 다운로드 후 재업로드한다.**

```
├── documents/elections/<term>.pdf
├── documents/problems/<yyyy-mm-dd>/<slug>.pdf
├── documents/discussions/<slug>.pdf
├── press/<term>/poster.png
└── brand/logo/<variant>.<ext>
```

- **Notion uuid를 키에 넣지 않는다.** 떠나는 게 목적인데 식별자를 물려받으면 의존이 남는다
- 한글 파일명은 슬러그화, 원본명은 매니페스트와 객체 메타데이터에 보존
- 확장자는 `Content-Type`으로 판정 (`2025-2`, `수문연_a_calculus_puzzle` 처럼 확장자 없는 항목이 있다)

접근은 **CloudFront + OAC**. 버킷은 퍼블릭 차단 유지, 버전 관리, SSE-S3.

### 4-4. 매핑표

```jsonc
// assets-manifest.json — 레포에 커밋
{
  "attachment:ef43a0d5-...:2026-1.pdf": {
    "s3Key": "documents/elections/2026-1.pdf",
    "originalName": "2026-1.pdf",
    "contentType": "application/pdf",
    "bytes": 123456,
    "sha256": "...",
    "sourcePage": "3042f5f5b3ac81099ab6de9f94e5883c"
  }
}
```

### 4-5. 파이프라인

```
1. 열거    loadPageChunk + queryCollection. ⚠️ 토글 재귀 필수 —
           이번 조사에서만 세 번 놓쳤고, 이미지 5개가 전부 토글 안에 있었다
2. 해석    서명 URL 재발급 (source 그대로는 403)
3. 다운로드 Content-Type / Content-Length 기록, sha256 계산
4. 정규화   슬러그화, 확장자 판정, sha256 중복 제거
5. 업로드   S3 PUT + 메타데이터
6. 검증    개수 90 일치, HEAD 200, 샘플 열람
7. 기록    assets-manifest.json 커밋
```

멱등성: sha256 기준으로 기존 파일은 건너뛴다. 중단·재실행이 안전해야 한다.
한 사진이 두 세미나에 걸릴 때 어느 키가 이기는지는 §6 A0에서 정한다.

## 5. 🔴 새로 만들어야 하는 것 — 이주 비용의 대부분

Notion이 사라지면 아래가 전부 없어진다. 데이터를 옮기는 것보다 이쪽이 크다.

### 5-1. 편집 UI

현행 `/admin`이 커버하는 것: 가입 승인, 세미나 개설 승인, 이벤트 발행/연결, 출석 큐 수정.
**커버하지 않는 것 = 새로 만들 것:**

| 대상 | 필요한 화면 | 비고 |
|---|---|---|
| 회원 231행 | 목록·검색·수정·임원 지정 | `임원` multi_select가 학기별 직책이라 UI가 단순치 않다 |
| 개인 정보 240행 | 수정 (본인/관리자) | 🔒 PII. 접근 로깅 |
| 활동 기록 76행 | 생성·수정·출석자 지정 | 출석자는 relation 다중 선택 |
| 세미나 기록 25행 | 생성·수정·**파일 업로드** | 강의 자료·활동 사진 |
| 스터디 기록 17행 | 생성·수정·**파일 업로드** | 앱에 읽기 코드조차 없다 |
| 회식 갤러리 2행 | 생성·**파일 업로드** | env조차 없다 |
| 정적 문서 (회칙 등) | §5-3 | |

`relation` 편집(출석자 지정, 진행자 선택)은 **회원 231명 중 다중 선택**이라
검색 가능한 피커가 필요하다. 미머지 `seminar` 브랜치가 이미 유사한 요구를 다루고 있으므로
[`seminar-events.md`](./seminar-events.md)와 함께 설계할 것.

### 5-2. 파일 업로드 경로

지금은 업로드 경로가 **없다.** 세미나 신청의 자료는 외부 링크 입력이고
(`seminar/apply/+page.svelte`의 `<input type="url">`), 과거 첨부는 Notion에 사람이 올린 것이다.

필요한 것:
- 앱이 **presigned PUT URL**을 발급 → 브라우저가 S3에 직접 업로드 (Vercel 함수 페이로드 한도 회피)
- 업로드 후 앱에 s3Key 등록 → 해당 레코드의 file 배열에 추가 (§2-2 `mutate` 경유)
- 타입·크기 제한, 파일명 슬러그화, 바이러스 스캔 여부 판단
- 고아 객체 정리 (업로드 후 등록 실패한 파일)

### 5-3. 정적 문서 편집

회칙(현행 + 개정본 2건), 역대 회장단, 홍보 자료, 선거 공약, Integration Bee, 문제 창작 활동.
Notion에서는 임원이 직접 고쳤다. 대체안:

| 안 | 장점 | 단점 |
|---|---|---|
| **레포 PR** | 이력·리뷰 무료, 구현 0 | 비개발자 임원이 못 고친다 |
| S3 마크다운 + 앱 내 편집기 | 임원이 고칠 수 있다 | 에디터·프리뷰·이력 UI를 만들어야 함 |
| 외부 헤드리스 CMS | 구현 최소 | Notion을 다른 SaaS로 바꾼 것뿐 |

**확정: 레포 PR** (D1). 회칙은 개정 시 투표를 거치는 문서라 이력이 중요하고, git이 그걸 공짜로 준다.
변동 빈도가 낮아 저장소 조회를 반복할 이유도 없다.

남은 실무 과제:
- 임원진용 **편집 가이드** (마크다운 문법, PR 여는 법) — 없으면 사실상 개발자 전용이 된다
- 회칙 개정본은 **파일을 갈아엎지 말고 새 파일로 추가**한다 (현재도 개정본 2건이 이력으로 남아 있다)
- 회장단 교체처럼 학기마다 반복되는 것은 **데이터로 뺄지 문서로 둘지** 판단
  (현재 랜딩은 회원 DB의 `임원` multi_select에서 임원을 끌어온다 — 문서와 데이터가 이미 섞여 있다)

## 6. 단계

```
── 0단계: 착수 전 반드시 ──────────────────────────────
P0-a  프로덕션 env 확보 → EVENTS / ATTENDANCE_QUEUE 스키마·행 수 실측
P0-b  전 DB 원본 JSON 덤프 → 비공개·버전관리 버킷 (백업. 현재 유일 사본이 Notion 휴지통뿐)
P0-c  개인정보 누수 선차단: getLatestExecutives()를 루트 레이아웃에서 제거
P0-d  CRON_SECRET 설정 (현재 미설정 → sync-events가 공개 상태)

── A: 자산 ────────────────────────────────────────
A0    안정 id 체계 확정 + id-map.json 커밋 (자산 키가 여기 의존)
A1    자산 90개 열거 + 용량 실측 (토글 재귀 필수)
A2    버킷 2개 생성 (assets 공개 / data 비공개), CloudFront + OAC
A3    다운로드·정규화·업로드 (멱등)
A4    검증 + assets-manifest.json 커밋

── B: 레코드 ───────────────────────────────────────
B1    테이블 JSON 스키마 확정 (relation → 자체 id, formula 처리 방침)
B2    S3 데이터 계층 구현 — getTable / mutate(If-Match) / 캐시 연동
B3    익스포터: Notion → tables/*.json (자산은 s3Key로 치환)
B4    읽기 경로 전환 (Repository 계층). 이 시점까지 Notion이 원본
B5    쓰기 경로 전환 — 17개 호출부 / 10개 라우트

── C: 편집 (최대 작업량) ────────────────────────────
C1    파일 업로드 (presigned PUT + 등록 + 정리)
C2    관리자 편집 UI — 회원 · 활동 · 세미나 · 스터디 · 갤러리
C3    개인 정보 편집 + 접근 통제·로깅
C4    정적 문서 편집 경로 (§5-3 결정에 따름)

── D: 전환 ────────────────────────────────────────
D1    병행 기간 — Notion 읽기 전용 전환, 앱이 단일 원본
D2    최종 델타 익스포트 + 정합 검증
D3    Notion 공개 해제 → 워크스페이스 아카이브 (즉시 삭제 금지)
```

**A와 B는 병렬 가능. C는 B2 이후. D는 전부 끝난 뒤.**
페이지 이주([`notion-pages-to-web.md`](./notion-pages-to-web.md))는 A4 이후 페이지 단위로 착수.

## 7. 검증

| 항목 | 방법 |
|---|---|
| 행 수 | 테이블별 `count` == Notion 실측 (231/240/76/25/17/9/5/2 + EVENTS·QUEUE) |
| 자산 개수 | S3 객체 수 == 90 |
| 자산 무결성 | sha256 대조, HEAD Content-Length 일치 |
| relation 정합 | 모든 참조 id가 대상 테이블에 실재 (dangling 0). **9개 DB 전부 이주해야 성립** |
| 개인 정보 240 vs 회원 231 | 차이 9건이 가입 신청 9건과 대응하는지 확인 |
| 동시 쓰기 | `mutate()` 경합 테스트 — 두 요청이 같은 테이블을 칠 때 유실 0 |
| 쓰기 경로 회귀 | **10개** 라우트 전부 동작 (7개가 아니다 — §1) |
| 권한 | 비공개 버킷이 CloudFront/퍼블릭으로 노출되지 않음 |
| 복구 | 잘못된 쓰기를 S3 이전 버전으로 되돌릴 수 있음 |

## 8. 결정 필요

1. ~~정적 문서 편집 수단~~ → **확정: 레포 PR** (D1)
