# `src/lib/server/data/schemas/mail-rule-history.ts` (21줄)

**접두사 `LA17-`** · `mail-rule-history` 테이블 행 스키마 — 이벤트별 메일 규칙 세트의 직전 스냅숏(되돌리기 1단계).

## LA17-1 🟡 스냅숏 속 규칙 모양을 `MailRuleSchema`에서 파생하지 않고 다시 적었다 — 필드를 더하면 되돌리기가 조용히 잃는다

> **검증 정정**(주장 축소, 등급 유지): "`MailRuleSchema`만 고쳐도 컴파일은 통과한다"는 **필수 필드에 대해서는 틀리다.**
> `mutate`의 행 타입은 `z.infer`(출력 타입)라 `.default()`를 단 필드도 필수 속성이다 — 되돌리기의 행 재구성
> (`mail-admin.ts:372-379`)과 실체화(`:390-397`)가 새 필드 없이 객체 리터럴을 만들므로 **컴파일 오류가 난다.**
> 개발자는 그 자리에서 값을 정해야 하고, 이때 스냅숏 타입에 그 필드가 없으니 상수(예: `delayDays: 0`)를 넣기 쉽다 —
> 손실은 "오류 없이"가 아니라 "컴파일러가 물은 질문에 틀린 답을 하게 만드는" 방식으로 일어난다. `.optional()` 필드라면
> 본문 그대로 조용히 사라진다. 스냅숏 작성(`:338-344`)이 세 필드만 고르고 비엄격 스키마가 모르는 키를 벗긴다는 기전은 맞다.

11-17행의 `{ templateKey, recipient, enabled }`는 `MailRuleSchema`(`mail-rule.ts:17-20`)의 부분집합을 손으로 다시 쓴
것이다. 같은 세 필드가 서비스에서 또 두 번 손으로 나열된다 — 스냅숏 작성 `mail-admin.ts:338-343`, 되돌리기
`mail-admin.ts:371-379`. (`dispatch.ts:112,120-124`도 같은 모양이다.)

결과: 규칙에 필드를 하나 더하면(예: 발송 지연 `delayDays`) `MailRuleSchema`만 고쳐도 컴파일은 통과한다. 그런데

- 스냅숏 작성은 세 필드만 골라 담고(`:339-343`),
- 설령 다 담아도 이 스키마가 비엄격 `z.object`라 **모르는 키를 조용히 벗겨 낸다**(`tables.ts:139-142` — 게이트 결과를
  저장),
- 되돌리기는 세 필드로 행을 재구성한다(`:372-379`).

즉 되돌리기가 새 필드를 **오류 없이** 잃는다. `seminar.test.ts:215-217`이 바로 이 실패 모드("zod가 미지의 키를 조용히
벗겨내므로 저장 시 소실")를 다른 스키마에서 컴파일 시점에 묶어 둔 선례다.

처방: `rules: z.array(MailRuleSchema.pick({ templateKey: true, recipient: true, enabled: true }))`, 서비스 쪽은 그
타입을 받아 펼친다. 동작 변경 없음.

## 확인했고 지적하지 않은 것

- **`id` 필드가 없다** — 이 코드베이스에서 `id` 없는 유일한 테이블이다. 키는 `event`(이벤트당 1행)이고, 찾고 바꾸는
  곳(`mail-admin.ts:349-352,360-362`)이 모두 `event`로 한다. `id`를 가정하는 범용 코드(`setFileArray`, 자산 참조
  수집 등)는 이 테이블을 다루지 않는다. 결함이 아니다
- **`event`·`recipient`가 자유 문자열** — 같은 사안을 `mail-rule.ts`에서 한 번만 다룬다(`LA18-1`)
- **스냅숏 작성과 규칙 교체가 두 번의 `mutate`로 따로 커밋된다**(`mail-admin.ts:368-382`) — 원자성 문제는 서비스의
  것이다. `mail-admin.ts` 리뷰로 넘긴다
- **되돌리기 메커니즘이 셋이다** — 템플릿·변수는 행 안의 `previous`(`LA19-1`, `LA20-2`), 규칙은 별도 테이블. 규칙은
  "행 집합"의 스냅숏이라 행 안에 둘 수 없으므로 별도 테이블은 정당하다
