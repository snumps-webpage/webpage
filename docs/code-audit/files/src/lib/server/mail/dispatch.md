# `src/lib/server/mail/dispatch.ts` (184줄)

**접두사 `LB11-`** · 자동 메일 디스패처(S10). 이벤트 → 유효 규칙(mail-rules, 없으면 코드 기본) → 템플릿 렌더 → 수신자 해석 → 80명 배치 발송. 실패는 로그 + `false`.

## LB11-1 🟠 반환값이 "아무것도 안 나감"과 "일부만 나감"을 구분하지 못하고, 호출부는 그것을 "재발송해도 된다"로 읽는다

> **검증 정정**: 인과는 확인했다 — 발송은 수신자별이 아니라 **80명 Bcc 배치 단위**(157-165행)이고, 배치 예외는 잡혀
> `ok = false`로만 남으며 루프는 다음 배치로 계속된다. `false`의 뜻은 "하나 이상 실패"이지 "아무것도 안 나감"이 아니다.
> `announce`(`seminars.ts:146-158`)는 그 `false`에 `announcedAt`을 `null`로 되돌리고, "공지 재발송" 버튼
> (`SeminarPublicationCard.svelte:235-254`)은 `?/publishSeminar` → `flow_publish_seminar`가 다시 선점
> (`atomic_flows.sql:369-371`) → `emitMailEvent` 전체 재실행이므로 **이미 받은 배치가 다시 받는다.** 이중 발송 확정.
> 다만 둘째 예시의 원인 "템플릿 렌더 예외"는 틀렸다 — `renderMailTemplate`은 두 조회를 모두 삼켜(`template-store.ts:263-268,
290-302`) 사실상 던지지 않는다. 규칙 단위 실패의 실제 원인은 `executives` 해석의 `getTable` 실패, `LB11-3`의 목록 밖
> 수신자 값(`TypeError`) 등이다. 결론(회원 공지는 다 나갔는데 `false`)은 같다. 등급 유지.

`emitMailEvent`는 배치 하나라도 실패하면 `ok = false`(171행), 규칙 하나라도 실패하면 `ok = false`(176행)를
반환한다. 나머지 배치·규칙은 **이미 발송된 뒤**다.

호출부 `services/seminars.ts:146-158`(`announce`)은 `false`를 받으면 공지 선점(`announcedAt`)을 `null`로
되돌린다 — "다음 재실행이 재시도". 그 재실행(공지 재발송 버튼, 커밋 `29bae21`)은 **전 수신자에게 다시** 보낸다.

- 수신자 170명 → 배치 80·80·10. 셋째 배치만 실패 → 160명이 받았는데 `false` → 재발송 시 160명이 두 번 받는다
- 관리자가 `seminar.published`에 `admins` 규칙을 추가했고 그 규칙만 실패(예: 템플릿 렌더 예외) → 회원 공지는
  전부 나갔는데 `false` → 재발송 시 전 회원이 두 번 받는다

이는 두 곳의 명시적 결정과 모순된다 — 이 파일 171행 "재시도 없음 — 승인 재실행이 이중 발송하면 안 된다",
`seminars.ts:133-138` "중복 발송보다 이쪽을 택했다 — 전 회원 메일은 한 번 더 가는 것이 안 가는 것보다 나쁘다".
boolean 하나로는 호출부가 그 결정을 지킬 수 없다.

처방: 결과를 `{ attempted, sent, failed }`(또는 "하나라도 나갔는가") 형태로 넓히고 `announce`는 **아무것도
나가지 않았을 때만** 선점을 되돌린다. **동작 변경**(부분 실패 시 재발송 버튼이 나타나지 않게 된다).

## LB11-2 🟠 규칙 조회 실패 시 코드 기본 규칙으로 **열린 채** 떨어진다 — 관리자가 끈 메일이 다시 나간다

126-132행: `getTable("mail-rules")`가 어떤 이유로든 던지면 모든 이벤트가 `defaultRules`(전부 `enabled: true`)로
돌아간다. 관리자가 `enabled=false`로 끈 규칙(123행이 읽는 값)과 바꾼 수신자 라우팅이 조용히 무시된다.

일시 장애만이 아니다. `fetchRows`는 저장된 문서를 스키마로 디코드하고(`data/tables.ts:106`), 행 하나가
스키마를 어기면 **테이블 전체 읽기가 던진다.** mail-rules에 잘못된 행 하나가 생기면 그 순간부터 **모든 이벤트**가
기본 규칙으로 발송되며, 흔적은 `console.error` 한 줄씩뿐이다.

이 폴백의 근거로 적힌 "메일은 본 동작을 절대 막지 않는다"(13-14행)는 폴백 없이도 성립한다 — `emitMailEvent`의
바깥 `catch`(179-182행)가 이미 모든 예외를 `false`로 바꾼다. 즉 폴백이 실제로 고르는 것은 "막지 않는다"가
아니라 **"꺼진 메일을 보낸다"** 쪽이다. 같은 형태가 `template-store.ts`에 있다(`LB13-1`).

처방: 조회 실패 시 발송하지 않고 `false`. **동작 변경.**

## LB11-3 🟠 DB 규칙 행을 캐스트로 신뢰한다 — 허용되지 않은 수신자에게도 그대로 보낸다

허용 목록 검사는 쓰기 경로 하나(`services/mail-admin.ts:411`)에만 있다. `revertMailEvent`(`mail-admin.ts:369-381`)는
이력 행을 재검사 없이 되쓴다. 카탈로그가 선언한 불변식(`events.ts:27-28`)을 **발송하는 곳**이 확인하지 않는다 —
"상위 계층이 막아준다"는 감면 근거가 아니다(README 판정 기준).

처방: `effectiveRules`에서 `allowedRecipients`에 없는 행은 건너뛰고 로그. 잘못된 행에 대해서만 **동작 변경.**

## LB11-6 🟡 "유효 규칙" 산출이 세 곳에 있다

> **검증 정정**: 마지막 문장을 좁힌다. 조회 실패 시 목록 화면(`mail-admin.ts:293-310`의 호출부)은 규칙을 "다르게" 보여 주는
> 것이 아니라 **던져서 아무것도 보여 주지 않는다.** 정확한 서술은 "관리자는 오류를 보는 동안 디스패처는 기본 규칙으로
> 조용히 발송한다"이고, 이것은 `LB11-2`의 증상이다. 중복 지적 자체(세 사본)는 유지. `services/mail-admin.md`의
> `LB23-8`("네 곳")이 같은 중복을 관리 계층에서 센 것이다 — 두 지적은 한 수정(`resolveRules`)으로 함께 닫힌다.

"행이 있으면 행 전체, 없으면 `defaultRules`를 `enabled: true`로"가

| 위치                                         | 형태        | 조회 실패 시       |
| -------------------------------------------- | ----------- | ------------------ |
| 이 파일 109-133행 `effectiveRules`           | 규칙 배열   | 기본 규칙으로 폴백 |
| `services/mail-admin.ts:293-310` (목록 화면) | 화면용 뷰   | 던진다             |
| `services/mail-admin.ts:345-347` (스냅숏)    | 이력 스냅숏 | 던진다             |

에 각각 있다. 규칙 해석을 바꾸면(예: 기본 규칙과 행의 병합) 세 곳을 고쳐야 하고, 지금도 조회 실패 시
**화면이 보여 주는 규칙과 디스패처가 쓰는 규칙이 다르다.**

처방: 순수 함수 `resolveRules(rows, event)` 하나로 모으고 세 곳이 쓴다. **구조만.**
