# `src/lib/server/mail/client.ts` (98줄)

**접두사 `LB10-`** · Gmail 인프라 계층 — refresh token으로 액세스 토큰 발급·캐시, RFC 2822 원문을 조립해 Gmail API로 전송.

## LB10-1 🟠 헤더를 문자열 결합으로 만들면서 CR/LF를 거부하지 않는다

> **검증 정정**: 🟡 → 🟠. 초판의 감면 근거 "증상의 크기는 관리자 권한 안에 머문다"는 행위자·도달성 논거이고,
> 판정 기준상 등급을 내리는 근거가 아니다(초판 자신이 바로 뒤에서 그렇게 적는다). 이 결함 **자체**의 결과는
> 헤더 주입 — 동아리 발송 계정으로 임의의 `Bcc:` 다수에게 발송 — 이고, 그것은 `services/mail-admin.md`의
> **`LB23-6` 🟠과 같은 주입의 다른 층**이다: `LB23-6`은 입구(648·684행 무앵커 정규식)가 주소 하나를 보장하지 못하는 것,
> `LB10-1`은 싱크(64-66행)가 CR/LF를 중화하지 못하는 것. 실측 재확인: `/.+@.+\..+/.test("a@b.c\r\nBcc: x@y.z") === true`.
> 둘은 **한 경로를 두 곳에서 막는 관계**라 등급을 맞춘다. 수정 범위는 다르다 — 이쪽을 고치면 현재·미래의 모든 호출부에서
> 주입이 닫히고, `LB23-6`을 고치면 주입과 함께 `"a@x.com, b@y.com"` 다중 수신(이쪽 처방이 막지 못한다)이 닫힌다.
> 둘 다 필요하다. 다른 입구는 닫혀 있음을 확인했다 — `application.email`(`schemas/application.ts:12`)·`private-info.email`
> (`:9`)은 zod `email()`이고 제목은 base64 encoded-word(69행)라 제목 주입은 없다.

64-66행이 `recipients.join(", ")`를 그대로 `To:`/`Bcc:` 헤더에 넣는다. 주소에 `\r\n`이 있으면 임의 헤더가 삽입된다.

상위 검증은 균일하지 않다. `private-info.email`은 zod `email()`이 막지만, 관리자 테스트 발송의 주소 검사
`services/mail-admin.ts:648,684` `/.+@.+\..+/`은 **앵커가 없어** `"a@b.c\r\nBcc: x@y.z"`를 통과시킨다(실측).
증상의 크기는 관리자 권한 안에 머물지만, 헤더를 조립하는 층이 자기 입력을 검증하지 않는다는 사실은 그대로다 —
"상위 계층이 막아준다"는 감면 근거가 아니다.

처방: `dispatchEmail` 입구에서 수신자에 `[\r\n]`이 있으면 던진다. 정상 입력에는 **동작 변화 없음.**

## LB10-2 🟡 MIME 원문이 Gmail의 정규화에 기대고 있다

67-73행:

- `MIME-Version` 헤더가 없다 — RFC 2045상 `Content-Type`이 MIME으로 해석될 근거가 없다
- `Content-Transfer-Encoding`이 없어 기본값 `7bit`이 선언된 셈인데 본문은 8비트 UTF-8 한국어다
- 헤더는 CRLF(73행)인데 본문은 템플릿의 LF 그대로다(`template-store.ts`의 템플릿 리터럴)
- 69행 encoded-word는 줄 접기 없이 한 덩어리다. RFC 2047의 75자 제한을 `"[SNUMPS] 세미나 일정 변경 안내: 정수론 입문"`
  하나로 넘는다(88자, 실측)

지금 동작하는 것은 Gmail이 원문을 다시 쓰기 때문이다. 원문 자체가 선언과 내용이 다른 메시지다.

처방: `MIME-Version: 1.0`, `Content-Transfer-Encoding: base64`(본문 base64), 제목 인코딩 분할. **동작 변경**(수신측 바이트만).

## LB10-3 🟡 오류 경로가 원래 오류를 잃는다

93-96행: 실패 응답을 무조건 `response.json()`으로 읽는다. 앞단 프록시의 HTML 502처럼 JSON이 아닌 본문이면
`SyntaxError`가 던져져 95행 로그와 96행 `"Gmail API failure"`가 **둘 다** 사라지고, 상태 코드는 어느 경로로도
기록되지 않는다. 같은 파일의 토큰 경로(38-41행)는 `text()`로 읽어 이 문제가 없다 — 한 파일 안에서 두 방식이다.

처방: `text()`로 읽고 상태 코드와 함께 로그. **동작 변경**(로그·예외 문구만).

## LB10-4 🟡 토큰 응답을 검증하지 않는다

43-45행의 `data`는 `any`다. `response.ok`인데 `access_token`이 없으면 `undefined`를 `string`으로 반환하고,
호출부는 `Bearer undefined`로 보내 401을 받아 `"Gmail API failure"`로 기록한다 — 원인이 토큰 응답이라는
사실이 사라진다. `expires_in`이 없으면 `NaN`이 되어 캐시가 조용히 꺼진다. 300초 여유(45행)는 이름 없는 상수다.

저장소의 다른 외부 입력은 zod로 파싱한다. 이 경계만 예외다.

처방: `z.object({ access_token: z.string(), expires_in: z.number() })`로 파싱. 정상 응답에는 **동작 변화 없음.**

## LB10-5 🟡 토큰이 호출부로 새어 나가 "토큰 받고 → 보내기" 두 단계가 세 곳에 복제돼 있다

`dispatchEmail`이 `accessToken`을 첫 인자로 받으므로 모든 호출부가 `getAdminAccessToken()`을 먼저 부른다 —
`dispatch.ts:156-165`, `services/mail-admin.ts:667-673`, `:693-704`. 토큰은 이 파일의 내부 사정이다(캐시·만료 모두
여기 있다). 인증 방식을 바꾸면(서비스 계정 등) 세 호출부를 모두 고쳐야 한다.

51행 주석 "Internal helper"도 사실이 아니다 — 두 모듈과 배럴(`mail.ts:6`)이 export를 쓴다.

처방: `sendMail(recipients, subject, body, opts)`가 안에서 토큰을 얻는다. **구조만.**

## LB10-6 🟡 두 `fetch`에 시간 상한이 없다 (검증 추가)

27행(토큰)과 81-91행(발송) 모두 `signal`이 없다. 메일은 **커밋 뒤 요청 안에서 동기로** 기다려진다 —
`announce`(`services/seminars.ts:146`), 가입 거절(`routes/(admin)/admin/+page.server.ts:234`), 가입 신청
(`signup/+page.server.ts:113`) 등. Gmail·OAuth 연결이 응답 없이 걸리면 그 요청은 플랫폼이 함수를 죽일 때까지 선다.

- 상태는 이미 커밋됐는데 사용자는 성공 대신 타임아웃을 받는다 — `mailFailed`도 전달되지 않는다
- `announce`에서는 선점(`announcedAt`)과 되돌리기 사이에 프로세스가 죽는 창이 `seminars.ts:134-137`이 "남는 창"으로
  받아들인 좁은 틈이 아니라 **함수 수명 전체**로 넓어진다 — 공지는 안 나갔는데 "보냈다"로 남는다

`dispatch.ts:13-14`의 "메일은 본 동작을 절대 막지 않는다"는 예외에 대해서만 지켜지고 시간에 대해서는 지켜지지 않는다.
플랫폼의 강제 종료는 타임아웃이 아니다(README 판정 기준).

처방: 두 `fetch`에 `signal: AbortSignal.timeout(…)`. 정상 응답에는 **동작 변화 없음.**

## 확인했고 지적하지 않은 것

- **Bcc 모드(60-66행)** — 빈 그룹 `To: undisclosed-recipients:;`는 RFC 5322의 정당한 형태이고, 주석이 스팸 점수 이유를
  밝힌다. Gmail API는 발송 시 `Bcc:` 헤더를 제거한다
- **Google 엔드포인트 URL 하드코딩(27, 82행)** — 외부 서비스의 고정 주소다. 설정으로 뺄 이유가 없다
- **모듈 수준 토큰 캐시(7-8행)** — 서버리스 인스턴스마다 한 번 발급하는 것으로 충분하다. 동시 발급 중복은 무해하다
- **자격 증명 누락 시 던진다(23-25행)** — `emitMailEvent`가 잡아 `false`로 바꾼다. 문구의 ".env"는 배포 환경에서는
  부정확하지만 로그 문구 수준이다
- **토큰 오류 본문을 예외 메시지에 싣는다(40행)** — Google 토큰 엔드포인트의 오류 본문은 `error`·`error_description`뿐이고
  비밀을 되돌려주지 않는다
