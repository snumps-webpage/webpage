# `src/lib/server/services/membership.ts` (133줄)

**접두사 `LB26-`** · 가입 신청 수명주기(API-SPEC §4-1~4-3, §7-2) — 신청 조회·제출·본인 수정·본인 철회, 관리자 승인(흐름 `flow_approve_application` 호출)과 거절. 신청 표는 미처리 행만 담는다.

## LB26-1 🟡 저장할 때 정규화한 이메일을 읽을 때마다 다시 정규화한다 — 쓰기 불변식을 스스로 믿지 않는다

43행 `email: norm(input.email)` — 이 파일이 쓰는 모든 행의 `email`은 이미 정규형이다(신청 행을 만드는 다른 경로는 없다).
그런데 읽는 쪽 다섯 곳이 저장값에 `norm`을 다시 건다: 24, 47, 65, 81, 83행의 `norm(a.email)`.
SQL도 `lower(trim(v_app ->> 'email'))`로 또 한다(`atomic_flows.sql:692`).

두 해석이 가능하고 코드는 어느 쪽인지 말하지 않는다:

- 저장값이 정규형이라는 것이 불변식이면 → 읽기의 `norm(a.email)`은 불필요하다(입력 쪽 `norm(email)`만 남는다)
- 정규형이 아닌 행이 있을 수 있다면(이관·수동 입력) → 43행의 정규화는 방어가 아니라 **불완전한 이관**이고, 한 번 정리하고 끝낼 일이다

그리고 18행 `norm` 자체가 저장소에 여러 벌 있는 규칙의 한 사본이다 — `LA01-2`(서버 여섯 곳 + SQL).
정규화를 바꾸면(NFC 추가 등) 이 파일은 18행 한 곳이지만, 저장된 행과의 비교가 전부 그 규칙에 기대므로 이관이 필요한지 판단할 근거가 코드에 없다.

**고침**: 18행을 공용 `normalizeEmail`로 바꾸고, 저장값이 정규형이라는 것을 스키마(`ApplicationSchema`의 `email`에 `.transform`
또는 `refine`)로 못 박은 뒤 읽기 쪽 `norm(a.email)`을 지운다. **구조만 바뀐다**(이관된 비정규 행이 있으면 먼저 정리).

## LB26-2 🟡 비가시 문자 제거가 두 가지 철자로 쓰였다 — 필드를 더하면 한쪽만 따라온다

| 경로                           | 방식                             |
| ------------------------------ | -------------------------------- |
| `submitApplication` (38-42)    | 다섯 필드를 **이름으로 나열**    |
| `updateOwnApplication` (67-72) | 패치의 **모든 문자열 값**에 적용 |

`Application`에 텍스트 필드(예: 전공 세부)를 더하면 수정 경로는 자동으로 거르고 제출 경로는 빠뜨린다 — 제출 때 들어간 soft hyphen이
그대로 저장된다. `LA08-1`이 말한 "옵트인이라 새 경로가 빠진다"가 한 파일 안에서 재현된다.

또 67-72행의 `Object.fromEntries`는 타입을 `{ [k: string]: string }`로 지운다. 73행 `{ ...rows[idx], ...clean }`은
그 뒤로 어떤 키든 받는다 — 57-62행 `Pick`이 지키던 "이 다섯 필드만"이라는 제약이 함수 시그니처에서 끝난다.

**고침**: `sanitizeApplicationText<T extends Partial<Application>>(v: T): T` 하나를 두고 두 경로가 쓴다(또는 `LA08-1` 처방대로
스키마 층에서). **구조만 바뀐다.**

## LB26-3 🟡 "행을 찾거나 NOT_FOUND"를 세 가지 모양으로 쓴다

- 64-75행: `findIndex` → `-1`이면 `NOT_FOUND` → 치환
- 80-84행: `some`으로 확인 → `filter`로 제거 — 같은 비교를 두 번 돈다
- 126-132행: 콜백 밖 변수 `removed`에 담아 `removed!`로 꺼낸다

`members-admin.ts:14-27`(`patchMember`)·`:123-128`도 같은 일을 또 다른 모양으로 한다(`LB25-10`). 표 계층에 "키로 한 행 치환/제거,
없으면 `NOT_FOUND`" 헬퍼가 없어서 서비스마다 다시 쓴다. 126-132행의 non-null 단언은 `mutate`가 콜백을 **재시도**할 수 있다는 점
(`tables.ts:111-164`) 때문에 읽는 사람이 한 번 더 따져야 한다 — 마지막 시도의 값이 남으므로 맞지만, 그 추론을 요구하는 모양이다.

**고침**: `data/tables.ts`에 `replaceRow`/`removeRow`(찾은 행을 반환)를 두고 두 서비스가 쓴다. **구조만 바뀐다.**

## 확인했고 지적하지 않은 것

- **승인이 한 트랜잭션이다** (104-121) — 반려와의 경합을 `approve-application-flow.test.ts:77-116`이 고정한다. 새 행 id 셋을 재가입 경로에서도 만드는 것(116-118)은 SQL이 id를 만들지 않는다는 규약(`ATOMIC-FLOWS.md:51` "SQL이 id를 만들지 않아")의 결과다
- **`today: now.slice(0, 10)`** (113) — `nowKstIso()`가 `+09:00` 문자열이므로 앞 10자는 KST 날짜다. 옳다
- **대상 학기를 `currentTerm()`으로 고정한다** (101-102, 114) — 명시적 보류(DEFER) 결정이다
- **거절이 단일 문서 `mutate`다** (123-133) — ATOMIC-FLOWS §7 "옮기지 않은 것"(각종 반려). 삭제된 행이 주소의 유일한 사본이라 반환값으로 메일을 보내는 설계도 라우트 쪽 주석과 맞다(`admin/+page.server.ts:231-234`)
- **거절·본인 철회에 감사가 없다** — 스펙 §1-5 기록 대상이 아니다(`API-SPEC.md:150-156`)
- **`getApplicationForEmail`과 `resolve-member.ts:68` `hasApplication`이 같은 질문에 다른 규약으로 답한다** — `ZP-1`이 표로 다뤘다(정규화·오류 처리가 다르다)
- **라우트도 `studentId`에 `stripInvisibles`를 건다**(`signup/+page.server.ts:76`, `signup/edit/+page.server.ts:50`) — 검증 **전에** 정리하려는 것이고, 제거는 멱등이다. 이중 적용이 해를 끼치지 않는다
- **재가입 승인이 탈퇴 유예 중 회원의 상태를 되돌리지 않는다** — SQL 쪽 판단이고 `LA43`의 "지적하지 않은 것"이 다뤘다
