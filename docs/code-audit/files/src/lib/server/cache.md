# `src/lib/server/cache.ts` (159줄)

**접두사 `LB03-`** · 2단 캐시 `withCache`(인스턴스 로컬 `Map` + 선택적 Redis)와 `invalidateCache`. 운영 호출부는 `data/tables.ts` 하나(`getTable` 171행, `getQueue` 198행)와 무효화 두 곳(`tables.ts:155`, `flows.ts:45-47`).

> 이관 전 리뷰 `pre-migration/files/src/lib/server/cache.md`(CA-1~CA-17, 기준 `cd916f6`)를 현재 코드에 대고 재검증했다.
> 대응표는 문서 끝. **CA-13(삼킨 실패가 캐시된다)은 해소됐다** — 호출부가 `tables.ts` 하나로 줄었고 `fetchRows`는 던진다.

## LB03-1 🟠 무효화가 진행 중인 읽기에 의해 되돌려진다 — 주석의 불변식이 거짓이다 (`W-13` 재확인)

91행에서 `now`를 찍고 121행에서 fetcher를 기다리는 동안 같은 키에 `mutate`가 끝나면:

```
읽기 R: 121 fetcher 시작 ──(구 버전 읽음)────────────── 124 local.set(구 값) · 133 redis.set(구 값, PX 300000)
쓰기 W:                     writeDocIf → invalidateCache(151 local.delete · 154 redis.del)
```

삭제가 R의 쓰기보다 **먼저** 끝나므로 R이 구 값을 다시 심는다. 결과:

- Redis가 있으면: 구 값이 **300초**(`tables.ts:29`) 동안 전 인스턴스에 퍼진다. 다른 인스턴스는 110행 백필로 되끌어오므로 15초 로컬 캡이 방어가 되지 않는다
- **Redis가 없어도**: 쓴 인스턴스 자신의 로컬 맵에 구 값이 15초 산다. 저장 직후 303 → GET이 같은 인스턴스로 오면 **자기 변경을 못 본다**

42-45행 "Redis keeps the full TTL and stays consistent because every mutation deletes the Redis key"는 삭제를 **시점 사건**으로 보지 못한 문장이다.
`flows.ts:45-47`의 무효화도 같은 경쟁에 놓인다. PRIORITY `W-13`(🟠, 미처리)이 재현 스크립트로 실측했다.
처방(동작 변경): 키별 세대 카운터를 fetcher 진입 전에 읽고, `invalidateCache`가 올리며, 124·133행 쓰기 직전에 대조해 바뀌었으면 저장하지 않는다. Redis 쪽은 같은 세대를 값에 싣거나 Lua CAS.

## LB03-2 🟠 Redis 티어는 스키마 검증을 건너뛰고, 키에 버전·네임스페이스가 없다 (`CA-14`·`CA-17`)

`tables.ts`의 계약은 "읽기는 엄격하게 검증한다"다 — `decode`(`tables.ts:73-82`)가 봉투를 zod로 파싱하고 실패하면 던진다.
그런데 Redis 히트(103-112행)는 `JSON.parse(cached)`를 **`as T`로 그대로** 돌려준다. 키는 호출자가 준 `table_<name>` 그대로다(103·133·154행).

- 스키마를 바꾸는 배포(필드 추가·기본값 추가·이름 변경) 뒤 최대 300초 동안 **새 스키마를 한 번도 통과하지 않은 구 모양 행**이 읽힌다. 쓰기 경로(`mutateObject`)는 store를 직접 읽으므로 안전하지만, 읽기 경로는 구 모양을 새 타입으로 믿는다
- 같은 `REDIS_URL`을 공유하는 두 배포(프리뷰·운영, 두 브랜치)가 **같은 키 공간**에 쓴다

처방(동작 변경): 키 앞에 배포 식별자(또는 `SCHEMA_VERSION`과 빌드 id)를 붙인다. 배포가 곧 무효화가 된다.
CA-17(`as T` 무검사 단언)은 이 경로에서만 실질적이다 — 로컬 티어 값은 이미 `decode`를 거친 객체다.

## LB03-3 🟠 Redis 명령에 시간 상한이 없다 — 캐시가 캐시 대상보다 느려질 수 있다 (`CA-15`)

18-22행은 `connectTimeout: 5000`과 `maxRetriesPerRequest: 1`뿐이고 `commandTimeout`이 없다(ioredis 기본값: 무제한).
연결은 됐지만 응답이 없는 Redis에서 103행 `await redis.get(key)`가 멈추고, 114-116행 폴백은 **예외가 나야** 동작하므로 도달하지 않는다.
로컬 미스인 모든 `getTable`이 이 앞에 서 있으므로(로컬 캡 15초마다 전 표가 미스가 된다) 존 가드(`resolveMember`)부터 요청이 멈춘다.
`maxRetriesPerRequest`는 재시도 **횟수**를 줄일 뿐 시간을 제한하지 않는다. 처방: `commandTimeout` 수백 ms. 한 줄, 동작 변경.

## LB03-4 🟠 무효화 실패가 흔적 없이 사라진다 (`CA-5`)

- 155-157행: `redis.del` 실패를 빈 `catch`가 삼킨다. 무효화 실패는 성능 사건이 아니라 **정합성 사건**이다 — 구 값이 300초 산다. 로그 한 줄 없다
- 134-136행: `redis.set` 실패도 같다(이쪽은 성능 사건이라 조용해도 되지만 적어도 한 번은 알려야 한다)
- 25행: 핸들러가 `ECONNREFUSED`를 **골라서** 침묵시킨다. Redis가 안 떠 있는 것 — 가장 흔하고 조치가 명확한 장애 — 에서 캐시가 로그 없이 1단으로 퇴화한다
- 29행: `catch {`에 바인딩이 없어 초기화 실패의 이유가 사라진다

읽기 실패(114-116행)만 조용할 자격이 있다(폴백이 있다). 처방: 155행·29행에 로그, 25행 제외를 `dev` 한정 또는 최초 1회로. 로그만 늘어나는 변경.

## LB03-5 🟠 캐시가 공유 가변 참조를 내준다 (`CA-2`)

97행 `return local.data as T`와 124행 `localCache.set(key, { data, … })` — 저장한 객체 **자체**를 넣고 꺼낸다. 복사도 동결도 없다.
게다가 `tables.ts`의 `versionCache`도 같은 배열을 들고 있다(`tables.ts:100,107`). 한 배열을 **로컬 캐시·버전 캐시·모든 요청의 호출자**가 공유한다.

호출자가 `getTable` 결과를 제자리 `.sort()`하거나 행 객체에 대입하면, 그 변경이 이 인스턴스의 **다음 모든 요청**에 보이고 Redis 티어와 영구히 갈라진다.
현재 호출부를 표본 조사한 범위(`services/*`, `public/archive.ts`, `(admin)` 로드)에서는 모두 `.filter()`/`.map()` 뒤의 새 배열을 정렬한다 —
이관 전의 실제 오염 두 곳은 사라졌다. **그러나 캐시가 계약으로 막지 않으므로 규약은 호출자의 기억에만 있다.**
처방: 로컬 티어에 넣을 때 `Object.freeze`(깊게, 또는 최소 배열과 행) — 위반이 즉시 TypeError가 된다. 위반하는 호출부가 없다면 동작 변경도 없다.

## LB03-6 🟡 `skipCache`가 죽은 파라미터이고, 두 티어에서 뜻이 다르다 (`CA-1`)

운영 호출부 둘(`tables.ts:171,198`) 모두 `skipCache`를 넘기지 않는다. 테스트도 넘기지 않는다.
그런데 의미는 비대칭으로 남아 있다 — 124행 로컬 쓰기는 `skipCache`와 무관하게 항상, 130행 Redis 쓰기는 `!skipCache`일 때만.
"새로 읽어라"가 한 티어에만 반영되는 옵션이다. 되살리면 이관 전 CA-1이 그대로 재현된다. 삭제가 맞다(동작 변경 없음). `W-13`의 완료 기준에도 적혀 있다.

## LB03-7 🟡 로컬 TTL 산술이 세 경로에서 다르다 (`CA-3`·`CA-9`)

| 경로               | 로컬 만료                                           |
| ------------------ | --------------------------------------------------- |
| 미스 (126행)       | `localTtl(key, ttlMs, localTtlMs)`                  |
| Redis 백필 (110행) | `localTtl(key, Math.min(ttlMs, 60000), localTtlMs)` |

- 110행의 `60000`은 이름도 주석도 없는 **세 번째 캡**이다
- 그 결과 `tables.ts:45`가 얼린 표에 준 `LOCAL_TTL_FROZEN_MS = 120_000`은 **미스 경로에서만** 120초이고 백필 경로에서는 조용히 60초가 된다. 호출자가 문서화한 계약(`tables.ts:31-44`)이 경로에 따라 반만 성립한다
- 백필은 Redis에 남은 수명(`pttl`)을 보지 않는다. 299초째 값을 백필하면 로컬이 그 뒤로 더 산다
- 만료 기준 `now`는 fetcher **전**(91행)에 찍힌다 — fetcher가 걸린 시간만큼 로컬 수명이 짧아지고, 133행 Redis `PX`는 호출 시점 기준이라 두 티어가 또 어긋난다

처방: 110행 상수를 없애고(`localTtl`만 쓰게) 126행 직전에 `Date.now()`를 다시 읽는다. 백필 수명은 동작 변경.

## LB03-8 🟡 로컬 캡 정책이 데이터 계층의 키 이름을 안다

50-52행 `LOCAL_TTL_CAPS = [{ prefix: "table_", capMs: 15_000 }]` — 범용 캐시 모듈이 **데이터 계층의 키 명명 규칙**(`table_`)을 하드코딩한다.
면제는 반대편(`tables.ts:45-49,175`)에 있다. 한 정책("다른 인스턴스의 쓰기를 놓치는 상한")이 두 파일에 반씩 산다.

- 큐 키가 `table_attendance-queue_<id>`(`tables.ts:195`)인 이유가 이 접두사 규칙에 걸리기 위해서다 — 이름이 정책을 떠받친다
- 47-49행 주석이 스스로 "the table list lives in the data layer, not here"라고 말한다. 그렇다면 캡 값도 거기 있어야 한다

운영 호출부가 `tables.ts` 하나이므로 `tables.ts`가 모든 호출에 `localTtlMs`를 넘기고 이 표를 지우면 된다. 구조 변경, 동작 동일.

## LB03-9 🟡 정리·축출이 상한을 보장하지 않는다 (`CA-7`·`CA-8`·`CA-16`)

- 139-142행: 정리가 **미스 경로에서만, 5% 확률로** 돈다. 로컬·Redis 히트(97·112행)는 조기 반환하고, fetcher가 던지면(`SERVICE_UNAVAILABLE`, 봉투 오류) 도달하지 않는다. `MAX_LOCAL_SIZE`(40행)는 상한이 아니라 희망이다
- 71-79행: 초과분을 `Map` 삽입 순 앞에서 자른다. `.set()`은 기존 키의 순서를 바꾸지 않으므로 **자주 갱신되는 키가 먼저 버려진다** — LRU의 반대
- 상한 단위가 항목 수다. 항목 하나가 표 **전체**다
- 큐 키는 이벤트마다 하나씩 늘고(`listQueues`가 전부 읽는다, `tables.ts:219-229`) 줄지 않는다

정리를 `localCache.set` 시점으로 옮기고 초과분은 `expiry` 오름차순으로 자르면 확률도 추가 자료구조도 필요 없다. 동작 변경(축출 대상).

## LB03-10 🟡 전체 초기화가 없어 테스트 48개 파일이 키 목록을 손으로 든다

`invalidateCache(key)` 하나뿐이라 테스트는 `for (const t of [...]) await invalidateCache(\`table_${t}\`)`를 반복한다 —
**48개 테스트 파일**(`grep -rl invalidateCache src --include=*.test.ts`). `tables.ts:245-250`의 `_resetDataLayerForTests`는 `versionCache`만 비우고 이 모듈의 로컬 맵은 비우지 않는다.
한 테스트가 목록에 없는 표를 건드리면 **다음 테스트가 이전 테스트의 행을 본다** — 테스트 간 누수가 파일마다의 목록 정확성에 달려 있다.
`_resetCacheForTests()`(로컬 `clear`)를 두고 `_resetDataLayerForTests`가 부르면 48개 목록이 사라진다. 구조 변경.

## LB03-11 🟡 주석이 노션 시절에 머물러 있다

5-6행 "Optimized for serverless environments to reduce **Notion API** load", 115행 "Silently fail to **Notion** fetcher".
fetcher는 Supabase store 읽기다(`tables.ts:174`). 이 파일을 처음 읽는 사람은 캐시 대상과 TTL의 근거(노션 rate limit)를 잘못 잡는다. 문구만.

## 확인했고 지적하지 않은 것

- **`CA-13` 해소** — 이관 전에는 fetcher 다섯 곳이 오류를 삼키고 `[]`를 돌려 그것이 캐시됐다. 지금 fetcher는 `fetchRows` 하나이고, store 실패는 `SERVICE_UNAVAILABLE`로 던지며(`tables.ts:63-71`) 봉투 오류도 던진다(`:77`). `version === null`의 `[]`(`:95-98`)는 "표가 없다"는 사실이고 캐시해도 된다
- **`CA-6`(티어별 값 모양)** — 스키마에 `z.date`·`transform`·`Map`이 없어(`data/schemas/`) zod 출력이 JSON 왕복에 안정적이다. 남는 차이는 LB03-5의 참조 공유뿐이다
- **`CA-12`(`ttlMs = 0`)** — `0`을 넘기는 호출부가 사라졌다. LB03-6에서 `skipCache`를 지우면 이 계약이 필요한 경로도 사라진다
- **`CA-4`(in-flight 중복 제거 부재)** — 콜드 미스가 겹치면 각자 `readVersion`을 부르지만, 버전이 같으면 `tables.ts:100`이 파싱을 건너뛴다. 논리 결함이 아니라 부하 최적화의 부재다
- **`CA-11`(호출부 TTL 흩어짐)** — 호출부 TTL이 `tables.ts:29` 한 상수로 모였다. 이 파일의 남은 매직 넘버(60000·0.05)는 LB03-7·LB03-9에 포함했다
- **`lazyConnect`·모듈 스코프 클라이언트·`new Redis`의 try 감싸기**(16-32행) — 서버리스에서 옳은 형태다
- **`localTtl`의 `override`가 `Math.min`이다**(55행) — `localTtlMs`는 15초 캡을 벗어나게 할 뿐 `ttlMs`를 넘어서 늘리지 못한다. 로컬이 Redis보다 오래 살 수 없게 하는 올바른 제약이다
