**접두사 `LC10-`** · 가입 신청 입력 규칙(전화·학번·배경지식·개인정보 동의)과 신청 수정용 파생 스키마.

## LC10-1 🟠 전화번호·배경지식 규칙의 사본 (셋 중 하나), 그리고 셋 중 유일하게 다르다

> **검증 정정**: **`LC11-4`의 중복 — 이 문서에서 세지 않는다.** 항목 스스로 "상세는 `LC11-4`"라고 하고, 이 파일에만 있는
> 차이(`trim` 없음·다른 문구)도 `LC11-4` 표의 "가입 신청" 행에 이미 적혀 있다. `LC07-5`와 같은 처리다.
> 사실은 모두 맞다 — "`trim` 차이는 지금 결과를 바꾸지 않는다"도 확인했다: 정규식이 정확히 숫자 11자리를 요구하고,
> 숫자 11자리인 입력은 `normalizePhoneNumber`가 항상 공백 없는 `XXX-XXXX-XXXX`로 다시 쓰므로 `trim`이 결과를 가를 입력이 없다.

5-7행과 12-15행은 `members.ts:89-94,181-184`·`dashboard.ts:61-68`과 **같은 저장 필드**를 검증한다 —
신청서의 `phone`·`background`는 승인 시 그대로 `private-info`로 복사된다(`atomic_flows.sql:715,717,759,761`).
그 뒤 회원 본인(대시보드)과 관리자(회원 상세)가 같은 값을 **다른 사본**으로 다시 검증한다. 상세는 **`LC11-4`**.

이 파일의 사본만 다르다:

| 항목      | 여기 (5-7행)                            | `members.ts:91-94` · `dashboard.ts:61-64`     |
| --------- | --------------------------------------- | --------------------------------------------- |
| `trim()`  | **없음**                                | 있음                                          |
| 오류 문구 | "010-0000-0000 형식으로 입력해 주세요." | "전화번호는 010-XXXX-XXXX 형식이어야 합니다." |

`trim` 차이는 지금 결과를 바꾸지 않는다 — 호출부가 먼저 `normalizePhoneNumber`를 부르고(`signup/+page.server.ts:75`,
`signup/edit/+page.server.ts:49`) 그 함수는 숫자 10·11자리일 때 공백까지 지운다(`utils.ts:32-42`).
그러나 이것은 **규칙이 스키마가 아니라 스키마 + 호출부 정규화의 합**이라는 뜻이고, 그 합이 세 입구에서 각각 조립된다.
같은 사람이 같은 번호를 가입 때와 대시보드에서 다르게 틀리면 다른 문구를 본다.
**구조만 바뀐다**(문구 통일은 동작 변경).

## LC10-2 🟡 학번이 두 표기로 저장되고, 문구는 한 표기만 말한다

8-11행 `/^\d{4}-?\d{4,6}$/`는 `2024-12345`와 `202412345`를 모두 받는다(테스트가 둘 다 고정한다,
`membership-applications.test.ts:33-38`). 정규화하지 않으므로 **입력한 그대로** 신청서와 `private-info.studentId`에
저장된다(`services/membership.ts:41` — `stripInvisibles`뿐; 승인 시 `atomic_flows.sql:716,760`이 그대로 복사). 11행 문구는 "2024-12345 형식으로"라고 한 표기만 요구한다.

같은 학번이 하이픈 유무로 두 문자열이 된다. 지금 학번은 표시에만 쓰이지만(`AdminApplicationQueue.svelte:55-58`),
`schemas/private-info.ts:12-13`은 학번을 "신규 가입부터 필수 수집"하는 식별 정보로 적는다 — 이것으로 대조·중복 검사를
하는 순간 두 표기가 다른 사람이 된다. 받는 형태를 둘로 둘 거라면 `.transform`으로 한 표기로 저장해야 한다.
**동작 변경**(저장값).

## 확인했고 지적하지 않은 것

- **`agreement: z.literal("on")`(16-18행)** — HTML 체크박스의 기본 값이 `"on"`이다. 체크하지 않으면 필드가 없고
  `formText`가 `""`로 읽어 문구가 나온다(`signup/+page.svelte:86`이 그 키를 그린다). 맞다
- **수정 스키마가 동의를 뺀다(21-24행)** — 이미 동의한 신청의 수정에 재동의를 요구하지 않는 것이 의도이고 테스트가 고정한다
  (`membership-applications.test.ts:41-49`). 동의 사실은 최초 제출 때 기록된다
- **3행 "the single source"** — 가입·가입 수정 두 액션이 모두 이 파일에서 가져온다(`signup/+page.server.ts:12`,
  `signup/edit/+page.server.ts:11`). 가입 **내부**에서는 사실이다. 가입 밖의 사본은 LC10-1
- **이름·학과를 스키마가 받지 않는다** — Google 계정 이름에서 파싱한다(`signup/+page.server.ts:66-71`). 폼 입력이 아니므로 맞다
- **`studentId`의 `trim` 후 정규식** — 호출부가 `stripInvisibles`를 먼저 부르고 서비스가 한 번 더 부른다. 방어가 겹치지만
  이 파일의 문제는 아니다
