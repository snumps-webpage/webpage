# `src/lib/domain/account.ts` (133줄)

**접두사 `LC01-`** · 회원 설정의 두 폼(메일 수신 토글 · 탈퇴 신청 삼중 확인) 검증 규칙과 탈퇴 유예 종료일 계산.

## LC01-1 🟠 탈퇴 유예 기간이 두 규칙으로 정의돼 있고, 테스트는 운영이 쓰지 않는 쪽을 고정한다

> **검증 정정**: 등급(🟠)과 기전은 그대로 두고, 사실 세 가지를 고치고 중복을 적는다.
>
> 1. **"31일이 아닌 달이 끼면 하루가 어긋난다"는 틀렸다.** 두 규칙의 차이는 신청한 달의 길이로 정해진다. 31일인 달이면
>    달력 규칙이 하루 늦다. 표의 예(8월 28일 → 09-28 대 09-27)가 바로 이 경우이니, 문장이 자기 표와 모순된다. 30일인 달이면
>    두 규칙이 같다. 2월이면 달력 규칙이 1~2일 **이르다**(평년 2월 15일 → 달력 03-15, 30일 03-17). 따라서 어긋나는 것은 "30일이 아닌 달"이고,
>    방향도 한쪽으로 정해져 있지 않다.
> 2. **"규칙을 하나로 정하는 것은 사용자 결정"은 틀렸다.** 스펙이 이미 정했다. `API-SPEC.md:523`은 파기 대상을
>    "`requestedAt + 1개월` 경과"로 적고, `FUNCTIONAL-SPEC.md:130`은 "1개월 유예", 탈퇴 화면은 "1개월간 유예"(`:91,103`)라고 적는다.
>    그러니 이것은 확인할 항목이 아니라 스펙과 구현이 어긋난 것이다(README 교훈 넷). 처방 문단의 "30일을 택하면"이라는 가지는 스펙을 바꾸는 선택지로만 남는다.
> 3. **죽은 사본의 월말 처리**: 달력 1개월을 택하면 이 함수를 그대로 살리면 안 된다. `setUTCMonth`는 없는 날을 다음 달로 넘기므로
>    01-31이 03-03이 된다(평년 확인). 월 단위 기간은 마지막 달에 해당일이 없으면 그 달의 말일에 끝나는 것이 통례다(민법 제160조 ③). 그래서 02-28에서 멈춰야 한다.
>
> **중복**: 같은 결함을 `withdrawal.md` **LB27-1**(🟠, 검증 확인)이 이미 소유한다. 그 표는 이 함수(`account.ts:129-133`), 테스트 전용 호출,
> 08-28 예, 같은 처방까지 적는다. `time.md` LA09-4도 계산 두 벌을 센다. 백로그에서는 **한 건**으로 센다. 이 문서가 따로 맡는 것은
> 위 3(월말 처리)과 이 함수의 삭제 또는 이전이다.

129-133행 `withdrawalGraceEndsAt`은 **달력상 한 달**(`setUTCMonth(+1)`)을 더한다.
운영 경로는 이 함수를 한 번도 부르지 않는다 — 호출부는 `account.test.ts:44-48`뿐이다.
실제 유예 종료일은 `server/core/time.ts:7-8`의 `WITHDRAWAL_GRACE_MS = 30일`("single definition")로
두 곳에서 계산된다.

| 위치                                                                        | 규칙        | 2026-08-28 신청 시 |
| --------------------------------------------------------------------------- | ----------- | ------------------ |
| `domain/account.ts:129-133` (테스트만 호출)                                 | 달력 +1개월 | 2026-09-28         |
| `services/withdrawal.ts:53-55` (`/withdraw/pending`)                        | +30일       | 2026-09-27         |
| `services/members-admin.ts:180` → `admin/+page.server.ts:146` `graceEndsAt` | +30일       | 2026-09-27         |

결과:

- "유예 종료일"이라는 하나의 정책이 두 값으로 정의돼 있다. 스펙(`FUNCTIONAL-SPEC.md:130` "1개월 유예")과
  회원 화면(`settings/withdraw/+page.svelte:91` "1개월간 유예")의 문구에 맞는 쪽은 죽은 사본이고,
  운영은 30일이다. 31일이 아닌 달이 끼면 하루가 어긋난다
- `account.test.ts:44`의 제목 "calculates the one-month grace-period end"는 운영이 따르지 않는 규칙을 초록으로 유지한다.
  README가 말하는 "도메인 규칙의 절반은 테스트"가 여기서는 **틀린 절반**이다
- 죽은 사본은 자체 결함도 있다 — `setUTCMonth`는 넘치는 날짜를 굴린다. 01-31 신청은 03-03이 된다(2월 31일 → 3월 3일)

처방: 규칙을 하나로 정하는 것은 **사용자 결정**이다(30일인가, 달력 1개월인가). 어느 쪽이든 정의를 브라우저 안전한
`domain/`에 두고 서버가 가져다 쓰면 된다(`termOf`가 이미 그 형태다 — `server/core/semester.ts:19-21`).
30일을 택하면 이 함수를 지우는 구조 변경이고, 달력 1개월을 택하면 관리자·회원 화면의 날짜가 바뀌는 **동작 변경**이다.

## LC01-2 🟡 같은 파일의 두 검증기가 실패를 서로 다르게 조립한다

- 51-56행은 issue→필드 메시지 변환을 손으로 돈다. 같은 일을 하는 `fieldIssues`(`form-data.ts:11-40`)가
  있고, 이 파일도 113-117행에서 그것을 쓴다. 그 헬퍼 주석이 "The one way to turn a schema failure into per-field form messages"다
- 손으로 돈 쪽은 `path[0]`이 두 필드가 아닌 issue를 **버린다**(54행). `fieldIssues`는 그런 issue를 `_form`에 모아
  "no message is lost"를 보장한다. 현재 스키마는 두 필드뿐이라 버려지는 issue가 없지만, 스키마에 교차 필드 규칙을
  하나 더하면 그 메시지는 소리 없이 사라진다
- 반환 모양도 다르다: 메일은 `{ success:false, failure }`(57-64행), 탈퇴는 `{ ...result, failure }`(119-126행)로
  zod의 `error: ZodError`를 실어 나른다 — 한 객체에 `error`(ZodError)와 `failure.error`(`"VALIDATION_FAILED"`)가 함께 있다.
  `admin-seminars.ts:196-210`도 후자다

부수: `withdrawalValuesFromFormData`(67-75행)는 export돼 있지만 이 파일 밖 호출부가 없다.

처방은 구조 변경(51-56행을 `fieldIssues(result.error, ["type","enabled"])`로, 반환 모양 통일). 동작 변화 없음.

## LC01-3 🟠 메일 수신 유형이 세 곳에 따로 적혀 있다

> **검증 정정**: 🟡 → 🟠. 초판은 어긋나는 방향을 하나만 적었고, 그 방향은 크게 드러나는 400이다. **반대 방향은 조용한 유실이다.**
> 도메인 쪽(25-27행)에만 새 유형을 더하고 저장 스키마(`private-info.ts:16`)를 빠뜨리는 경우다. 토글은 검증을 통과하고, 액션이
> `mailPrefs: { ...rows[idx].mailPrefs, [type]: enabled }`를 만든다(`notifications/+page.server.ts:51-54`). 그런데 쓰기 게이트는
> 저장 스키마로 다시 파싱한 결과를 저장하고, 이때 모르는 키는 사라진다(`tables.ts:139-141` "unknown keys gone", 기본 `z.object`는 strip).
> 새 키는 버려지지만 액션은 `{}` 성공을 돌려준다. 회원은 "수신 거부"가 저장됐다는 응답을 받는데, 실제로 저장된 것은 없다.
> 같은 부류(`LA06-1`)를 🟡로 둔 근거가 "조용한 오염이 없다"였다. 이 목록은 그 근거가 성립하지 않는 방향을 가진다.
> 처방은 그대로다(도메인 상수 하나에서 저장 스키마와 기본값을 파생).

25-27행의 `z.literal("announcements")`는 저장 스키마 `server/data/schemas/private-info.ts:16`
`mailPrefs: z.object({ announcements: z.boolean() })`의 키 목록과 같은 집합이고, 로드 기본값
`settings/notifications/+page.server.ts:24` `{ announcements: true }`가 셋째다.
유형을 하나 더하면(예: 세미나 공지) 세 곳을 함께 고쳐야 하고, 어긋나도 컴파일러가 잡지 않는다 —
도메인 쪽을 빠뜨리면 새 유형의 토글이 "지원하지 않는 알림 유형입니다."로 400을 받는다.

처방: 유형 목록을 도메인 상수 하나로 두고 저장 스키마와 기본값이 그것에서 파생되게 한다. 구조 변경.

## 확인했고 지적하지 않은 것

- **이름 비교의 trim 계약**(95-97·102행) — zod v4의 `.trim()`은 값을 바꾼 뒤 `superRefine`에 넘긴다. 서비스도
  `confirmName.trim()`을 보내고(`services/withdrawal.ts:31`), SQL은 저장된 이름과 `is distinct from`으로 비교한다
  (`atomic_flows.sql:1034-1036`). 폼·서비스·SQL 세 층이 같은 비교를 한다. `expectedName`을 trim하지 않는 것도 SQL과 같다
- **폼 검증과 SQL 재검증의 중복** — 77-80행 주석대로 폼은 필드별 메시지(UX), SQL은 원자적 판정(권위)이다. 역할이 다르다
- **`enabled`의 엄격한 enum**(28-30행) — 잘못된 값이 조용히 `false`(수신 거부)로 읽히던 결함을 막는 의도다(`notifications/+page.server.ts:42`). 테스트(`account.test.ts:9-18`)가 고정한다
- **체크박스를 `=== "on"`으로 읽음**(71-72행) — HTML 체크박스의 기본 값이다. 다른 값은 미확인으로 읽혀 fail-closed다
- **이름 200자 상한**(99행) — 메시지가 있고 저장 계층 제약과 충돌하지 않는다
