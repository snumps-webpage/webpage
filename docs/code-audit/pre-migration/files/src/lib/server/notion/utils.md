## U-1 🔴 검증하지 않는 검증기

`:11-24`

```ts
const result = schema.safeParse(data);
if (!result.success) {
  console.error(">>> [Notion Validator] Schema Mismatch:", result.error.format());
  return data as T;   // ← 원본 그대로
}
```

이름이 `validateNotionResponse`이고 반환 타입이 `T`인데, **실패해도 `T`인 척하는 아무 값이나 돌려준다.**

주석은 *"Fallback to raw data in production to avoid crashing"*이라고 적는다.
그런데 **`dev` 분기가 없다.** 개발 중에도 똑같이 통과시키므로
개발자가 불일치를 발견할 기회 자체가 없다 — 콘솔 한 줄이 전부다.

`schema.md` SC-9·SC-10에서 실측한 결과, **지금 이 순간 프로덕션에서**:
- 회원 목록 조회마다 **231건** 실패
- 개인정보 목록 조회마다 **13건** 실패

전부 통과한다. 로그만 쌓인다.

**제안**: 셋 중 하나를 고른다.
1. **던진다** — 호출부가 처리. 가장 정직하나 회귀면이 넓다
2. **안전한 기본값으로 치환한다** — 스키마에 `.catch()`나 `.default()`를 붙여
   zod가 복구하게 한다. 이 규모엔 이게 맞아 보인다
3. **검증을 포기하고 타입 선언으로만 쓴다** — 그러면 이 함수를 지운다

**지금은 셋 다 아니고, 검증이 있다는 착각만 준다.**

## U-9 🟠 `date`가 종료일을 버린다

`:46-47`

```ts
case "date":
  return property.date?.start ?? "";
```

Notion `date` 속성은 `{ start, end, time_zone }`이다. **`end`가 버려진다.**

실측: **활동 76행 중 20행이 기간을 갖는다.**

```
현대대수학          2025-12-23 → 2026-02-12    ← 학기를 걸친다
가환대수            2026-03-13 → 2026-05-29
푸리에해석과 응용     2025-09-05 → 2025-12-05
복소해석            2026-03-16 → 2026-03-31
26-겨울 KUSP 교류회  2026-02-07 → 2026-02-09
...  (총 20건)
```

하류에서 `+page.server.ts:199`가 `getSemesterKeyFromDate(a.date)`로 학기를 배정하므로,
**두 학기에 걸친 스터디가 시작 학기에 통째로 귀속된다.**

`getPropertyValue`의 일이 "값을 단순화하는 것"이라면 **무엇을 버리는지가 핵심 질문**인데,
이 케이스는 정보의 절반을 조용히 버린다.

**제안**: `{ start, end }`를 반환하거나 최소한 `end`가 있을 때 호출부가 알 수 있게 한다.
현재 `Activity.date: string` 계약을 바꾸는 일이라 하류 영향이 있다.

## U-3 🟠 `any` 하나가 하류의 **정적** 타입을 무력화한다

`:29` `export function getPropertyValue(property: any): any`

**반환이 `any`이므로 이 함수를 거친 값은 무엇에든 대입된다.**

- `admin.ts:83`의 `Promise<Application | null>`에서 `accepted: boolean`인데
  `""`가 들어와도 **컴파일된다**(`applications.md` AP-8)
- `activities.ts:56`의 `attendees`가 배열이 아니라 `""`일 수 있는데
  `+page.server.ts:188`이 `.includes()`를 부른다(`activities.md` AC-11)
- `MemberRepository.findAll(): Promise<Member[]>`가 `privateInfoId`가 있다고
  약속하는데 없다(`schema.md` SC-9)

> **초판 정정**: 초판은 "스키마도 전부 이 한 줄 뒤에서는 장식이다"라고 썼다. **틀렸다.**
> zod `safeParse`는 **런타임**이라 정적 타입과 무관하게 돈다 — U-1이 스스로 증명한다
> (캐시 미스마다 231+13건이 실제로 실패한다). 스키마를 장식으로 만드는 것은 `:21`이지 `:29`가 아니다.
> 그리고 위 세 사례 중 둘(`applications.ts`·`activities.ts`)은 **스키마를 아예 쓰지 않는다.**

정확히 말하면: **인터페이스와 Repository 반환 타입이 무력화된다.**
런타임 검증은 U-1이 별도로 무력화한다. 두 문제는 원인이 다르다.

파일 상단의 `eslint-disable`(`:1`)은 입력 `property: any`에 대해서는 정당하다 —
Notion 응답은 실제로 비정형이다. **정당하지 않은 것은 반환이다.**

**제안**: 유니온을 반환한다.

```ts
type NotionValue = string | number | boolean | string[] | undefined;
export function getPropertyValue(property: unknown): NotionValue
```

> `undefined`를 포함해야 U-4의 제안(부재를 `undefined`로 구분)과 어긋나지 않는다.
> 초판의 유니온은 `undefined`를 빼서 **두 절이 서로 모순됐다.**

호출부가 좁히도록 강제되면 AC-11 같은 것이 컴파일 타임에 잡힌다.
더 나아가 타입별 접근자(`getText`, `getRelationIds`, `getCheckbox`)로 나누면
반환 타입이 정확해지고 U-2도 `getRelationIds`에서만 다루면 된다.

## U-4 🟠 `""`가 네 가지를 동시에 뜻한다

| 위치 | 상황 | 반환 |
|---|---|---|
| `:30` | 속성 자체가 없음 | `""` |
| `:67` | 처리할 줄 모르는 타입 | `""` |
| `:71` | 파싱 중 예외 | `""` |
| `:35` 등 | **진짜 빈 텍스트** | `""` |

**넷을 구분할 방법이 없다.**

그래서 Notion에서 속성 이름이 바뀌면 — `seminars.md` S-1에서 실제로 일어난 일 —
모든 값이 조용히 빈 문자열이 되고, 코드는 "데이터가 비어 있다"고 해석한다.

그러면 스키마의 `.optional()`이 의미를 갖고, 스키마 불일치가 실제로 잡힌다.

## U-5 🟠 `multi_select`만 문자열로 접힌다

## U-6 🟠 `formula` 케이스가 없다

실 API로 전 DB 속성 타입을 훑은 결과, **처리되지 않는 타입은 `formula` 하나**이고
실제로 두 곳에 쓰인다:

```
MEMBERS.회원 단계          (formula)
ACTIVITIES.캘린더 표시 여부  (formula)
```

둘 다 `default:`(`:66-67`)로 떨어져 **`""`가 된다.**

현재 이 두 속성을 읽는 코드가 없어 피해는 없다. 그러나
`migration/notion-db-to-s3.md` §8-8이 "formula를 코드로 옮길지 필드를 없앨지"를
결정 사항으로 올려두었고, **옮기기로 하면 이 함수부터 고쳐야 한다.**

> **초판 정정**: "나머지 13개 타입은 전부 처리된다"고 썼는데 근거 없는 수다.
> 7개 DB 전체에 실재하는 속성 타입은 **11종**
> (rich_text 12 · relation 10 · title 7 · checkbox 3 · select 3 · files 3 ·
> formula 2 · date 2 · email 2 · phone_number 2 · multi_select 1).
> `formula`를 빼면 **10종**이 처리된다. `switch`의 케이스는 **14개**다.
> 셋 중 어느 수로도 13이 나오지 않는다.

> 뒤집어 보면 **케이스 14개 중 4개가 도달 불가능**하다 —
> `number` · `url` · `status` · `people`이 어느 DB에도 없다.
> 초판은 `number`와 `status`만 언급하고 `url`·`people`은 놓쳤는데,
> 하필 `people`(`:61`)을 U-5의 일관성 논거로 인용하고 있었다.

`client.ts`의 반환이 `any`라 이 접근이 옳은지 타입으로 확인할 방법이 없다.

## U-8 🟡 `try/catch`가 진짜 버그를 삼킨다

`:69-72`가 예외를 잡아 `""`를 반환한다.

`switch` 안의 코드는 전부 `?.`와 `|| []`로 방어돼 있어 **정상 입력에서는 던질 일이 거의 없다.**
즉 여기 걸리는 건 대체로 **예상 못 한 응답 형태**, 곧 진짜 조사할 가치가 있는 것이다.

그것이 `console.warn` 한 줄과 빈 문자열이 되어 U-4의 구분 불가에 합류한다.

## 지적하지 않은 것

- **파일 전체 `eslint-disable`**(`:1`): 입력이 실제로 비정형이므로 `property: any`는 정당하다.
  콜백 파라미터 6개(`:35,38,45,59,61,64`)도 마찬가지. **정당하지 않은 것은 반환 타입이고
  그건 U-3으로 올렸다**
- **`number`가 `?? 0`을 쓰는 것**(`:41`): U-4와 같은 부류지만 이 코드베이스에
  `number` 속성이 **하나도 없다**(실 API 확인). 도달하지 않는 코드에 대한 지적은 값어치가 없다
- **`status` 케이스**(`:56-57`): Notion의 `status` 타입 속성은 이 워크스페이스에 없지만,
  `select`와 다른 별개 타입이므로 **미리 처리해 둔 것이 맞다**
- **테스트 존재**(`utils.test.ts`, 8케이스): 이 디렉터리뿐 아니라 **레포 전체에서 유일한 테스트 파일**이다
