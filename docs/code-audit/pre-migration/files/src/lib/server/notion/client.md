## C-1 🔴 오류 구분 불가 → 이벤트가 아카이브된다

모든 함수가 실패를 **동일한 `Error`**로 던진다(`:79`, `:144`, `:173`, `:198`, `:221`, `:251`).
호출부에서 404·429·500·네트워크 오류가 전부 같은 모양이다.

연쇄:

```
client.ts:209  notionRetrieve      →  실패 시 구분 없는 Error
notion/events.ts:142  catch { return false; }      ← 모든 오류를 "페이지 없음"으로 해석
routes/events/[id]/[type]/+page.server.ts:29  await deleteEvent(event.id);
```

> **초판 정정 ①**: 초판은 "이벤트를 **영구 삭제**"라고 썼다. **틀렸다.**
> `deleteEvent`(`events.ts:105`) → `deleteEventInNotion`(`notion/events.ts:95`) →
> `export const deleteEventInNotion = notionArchive` → `PATCH {archived:true}`.
> **Notion 휴지통으로 가고 복구 가능하다.** 초판은 C-3 본문에 `notionArchive`를 직접 나열해
> 놓고도 세 파일 건너의 결과를 확인하지 않았다.

> **초판 정정 ②**: 초판은 이 경로를 "출석 체크인 화면"이라 표현해 **오히려 축소**했다.
> 실제 라우트 순서는:
> ```
> :17  ensureSession(locals, url)              ← 유일한 관문
> :24  checkPageExists → :29 deleteEvent       ← 파괴적 분기
> :34  if (event.status !== "active") 403      ← 그 뒤
> :37  if (params.type !== event.attendCode)   ← 그 뒤
> ```
> **파괴적 분기가 상태 검사·출석코드 검사보다 먼저 돈다.**
> 로그인한 회원이 `pathId`만 알면 종료된 이벤트에 아무 코드나 붙여 접근해도 이 경로에 닿는다.

**추가 사실**: `checkPageExists`는 `withCache`를 거치지 않고 `notionRetrieve`를 직접 부른다.
체크인 페이지 로드 1회 = **캐시 없는 Notion 요청 1회**. C-2와의 결합을 실제로 만드는 지점이 여기다.

> **근본 원인은 이 파일이 아니다.** 초판은 "근본 원인은 여기다"라고 썼는데, 리뷰 중인 파일이
> `client.ts`라서 나온 편의적 결론이다. 진짜 문제는 **GET 성격의 `load` 안에서 읽기 실패를 이유로
> 파괴적 쓰기를 한다**는 것이다. 오류 타입을 도입하면 트리거가 좁아질 뿐,
> 페이지 로드 중 삭제로 정합성을 맞추는 설계 자체는 페이지가 실제로 없을 때도 잘못이다.

**수정 순서**
1. **즉시(한 줄)**: 라우트의 `load`에서 `deleteEvent` 호출을 제거하거나,
   `checkPageExists`가 404가 아닌 오류를 다시 던지게 한다. 리팩터링 없음, 회귀면 없음
2. **그 다음**: 상태 코드를 담은 오류 타입 도입
   ```ts
   export class NotionApiError extends Error {
     constructor(readonly status: number, readonly code: string, message: string) { super(message); }
     get isNotFound()  { return this.status === 404; }
     get isTransient() { return this.status === 429 || this.status >= 500; }
   }
   ```

## N-1 🔴 `ok` 검사 전에 `json()`을 부른다

`:75`, `:140`, `:169`, `:217`, `:247` — 여섯 함수 중 **다섯**이 이 순서다:

```ts
const data: any = await response.json();   // 먼저
if (!fetchRes.ok) { ... }                  // 나중
```

Notion이나 엣지 프록시가 **JSON이 아닌 본문**을 돌려주면 — 502/504 HTML 페이지, 빈 503 —
`response.json()`이 `SyntaxError`를 던지고 **`!ok` 분기에 도달하지 못한다.**
즉 상태 코드는 버려지는 게 아니라 **읽히지도 않는다.**

던져지는 오류는 `Unexpected token '<' ...`이고, 그게 C-1의 연쇄를 그대로 탄다.
**C-1이 가정한 5xx 시나리오의 실제 발생 경로가 이쪽이며, 더 흔하다.**

예외는 `notionArchive`(`:195-196`)뿐이다 — `!ok` 안에서만 파싱한다. **이게 유일하게 맞다.**

**제안**: `if (!response.ok)`를 먼저 확인하고, 오류 본문 파싱은 `try`로 감싼다
(본문이 JSON이 아닐 수 있으므로).

## C-2 🟠 레이트 리밋·재시도가 없다

Notion API는 평균 **초당 3요청** 제한에 429와 `Retry-After`를 준다(공식 문서 확인).
`grep -rni "retry\|backoff\|429" src/` → **0건**. 재시도가 코드베이스 어디에도 없다.
(`cache.ts:19`의 `maxRetriesPerRequest`는 Redis용이다.)

`notionQuery`(`:65`)의 루프는 **간격 없이 연속 호출**한다.
`getAllMembers`(231행)·`getAllPrivateInfo`(240행) 모두 `page_size` 없이 부르므로
기본 100건 × 3페이지가 연달아 나간다.

> **초판 정정 ③**: 초판은 이걸 🔴로 뒀다. **C-1에서 심각도를 빌려온 것이다.**
> 단독으로는 페이지 로드 1회 실패다. C-1의 파괴적 경로를 막으면 즉시 🟠로 떨어진다.

**제안**: 429·5xx에 `Retry-After` 기반 지수 백오프. 모든 호출이 이 파일을 지나므로 한 곳이면 된다.

## N-4 🟡 `page_size` 종료 조건이 필터링된 집합을 센다

`:82-84`가 `"properties" in page`로 결과를 거른 뒤,

## 지적하지 않은 것

- **`NOTION_VERSION` 하드코딩**(`:8`): API 버전 고정은 올바른 관행이다
- **`notionArchive`가 성공 시 json을 파싱하지 않는 것**: 반환이 `void`라 맞다.
  **덧붙여 이 함수만 `!ok` 안에서 파싱하는데, 그게 N-1 기준으로 유일하게 옳은 형태다**
- **파일 전체 `any` 허용**(`:1`): Notion 응답이 실제로 비정형이라 이 파일은 정당성이 있다.
  초판은 이걸 C-10으로 지적했다가 본문에서 스스로 정당하다고 인정했다 — **지적이 아니므로 철회한다.**
  다만 입력 파라미터(`options: any`, `properties: any`)에 최소 타입을 주면 속성명 오타가
  런타임 400 대신 컴파일 타임에 잡힌다 — 이건 N-2와 함께 다룰 여지가 있다

> **초판이 여기 넣었다가 뺀 항목**: "페이지네이션 루프 구조가 정확하다"는 면죄부를 줬는데,
> N-2·N-3·N-4가 전부 그 루프 안에 있다. **면죄부는 지적보다 강한 주장이다** —
> 유지보수자에게 그만 보라고 말하는 것이기 때문이다. 철회했다.

`filter_properties`(`:53-56`)는 `members.md`의 2차 실측 검증 참조 —
불투명 ID를 가진 `학과` 속성으로 재확인했고 코드가 맞다.
