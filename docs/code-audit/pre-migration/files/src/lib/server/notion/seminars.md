## S-1 + S-2 🔴🔴 세미나 신청 기능이 통째로 죽어 있다

**두 개가 아니라 하나의 결함이다.** 초판은 읽기(S-1)와 쓰기(S-2)를 나누고
우선순위를 1·2번으로 갈라 놓았는데, **따로 고치면 기능이 살아나지 않는다.**

### 원인

`NOTION_PROPS.SEMINAR_FILES`(= `"강의 자료"`)가 **세미나 신청 내역 DB에 존재하지 않는다.**
실 API로 두 스키마를 조회했다:

```
세미나 기록      : 활동 사진(files), 진행자(relation), 학기(select),
                   비고, 진행자 (비회원), 강의 자료(files), 제목
세미나 신청 내역 : 설명, 진행자(relation), 예상 소요 시간, 승인됨(checkbox), 선수 지식, 제목
                   └ "강의 자료" 없음
```

코드는 이 속성을 신청 DB에 대해 **세 곳에서** 쓴다:

| 위치   | 동작                          | 결과                       |
| ------ | ----------------------------- | -------------------------- |
| `:86`  | `filter_properties`에 포함    | 조회가 **항상** 400        |
| `:153` | 생성 시 `{url}` 기록 (조건부) | 첨부 있는 신청 생성 400    |
| `:193` | 수정 시 `{url}` 기록          | **수정이 항상 400** — 아래 |

재현 (실 API):

```
코드가 보내는 조합 그대로 → HTTP 400 validation_error
  "The provided `filter_properties` contains an invalid attribute: 강의 자료"
"강의 자료"만 제외        → HTTP 200, 5행 정상
```

### 🔴 수정 경로는 **무조건** 실패한다

초판은 "첨부 있는 신청은 생성·수정도 실패한다"고 조건부로 썼다. **수정은 조건이 없다.**

```
seminar/edit/[id]/+page.server.ts:88   const attachment = data.get("attachment") as string;
                                        └ 빈 입력은 "" 이지 undefined 가 아니다
notion/seminars.ts:192                 if (data.attachment !== undefined)   ← 항상 참
```

이 라우트에서 오는 모든 저장이 `강의 자료`를 기록하려 하므로 **100% 400**이다.

**따라서 `:86` 한 줄만 고치면 목록·승인·반려는 살아나지만 수정 화면은 여전히 저장이 안 된다.**
초판의 "한 줄로 죽은 기능이 살아난다"는 틀렸다.

### 아무도 모르는 이유

`seminars.ts:25-34`가 삼킨다:

```ts
catch (e) { console.error("Failed to fetch seminar requests from Notion:", e); return []; }
```

**오류가 "신청 없음"과 구분 불가능한 모양으로 나온다.**
`withCache`는 fetcher를 `await`하므로 예외가 캐시 진입 전에 터진다 — 오염된 캐시도 없고,
**매 호출이 Notion까지 가서 400을 받는다.**

### 호출부 6곳 — 사용자가 실제로 보는 것

| 호출부                                         | 증상                                                                            |
| ---------------------------------------------- | ------------------------------------------------------------------------------- |
| `seminars.ts:112` → `admin/+page.server.ts:59` | **관리자 패널에 `세미나 개설 신청 (0)`과 빈 상태**. 헤드라인 증상을 만드는 지점 |
| `+page.server.ts:171`                          | 대시보드 내 신청 내역 항상 비어 있음                                            |
| `admin/+page.server.ts:233` (승인)             | `find` → undefined → `"Seminar request not found"`                              |
| `admin/+page.server.ts:281` (반려)             | 동일                                                                            |
| `seminar/edit/[id]/+page.server.ts:23`         | `find` → undefined → `:34` 홈으로 조용히 리다이렉트                             |
| `api/admin/seminar-requests/+server.ts:14`     | 항상 `[]`                                                                       |

> 초판은 "6곳"이라 쓰고 5개만 표에 적었다. 빠진 것이 하필 **헤드라인 증상을 만드는 경로**였다.

부수 발견: `edit/[id]/+page.server.ts:22-30`의 `try/catch`는 **죽은 코드**다.
`getSeminarRequests`가 던지지 않으므로 그 분기에 도달할 수 없고,
사용자는 `:34`의 리다이렉트를 받아 "그런 신청 없음"과 구분하지 못한다.

### 데이터는 멀쩡히 있다

```
초한 귀납의 다양한 활용     승인됨 False   2026-08-21   ← 대기
Test                        승인됨 False   2026-08-21   ← 대기(테스트 행)
PDEs for cell movements...  승인됨 True    2026-04-25

```

**대기 2건(실질 1건)이 관리자 화면에 뜨지 않고 승인할 방법도 없다.**

기존 5행이 존재할 수 있었던 이유: 생성 경로의 첨부 기록은 `if (data.attachment)` 조건부라
빈 URL 입력(`""`, falsy)이면 건너뛴다. **첨부 없는 신청만 접수돼 왔다.**

### 수정 — 하나로 묶어서

1. `:86`에서 `SEMINAR_FILES` 제거
2. `:153`·`:193`의 기록 제거 (또는 S-13 결정에 따라 목적지 재지정)
3. `:108-110`의 `attachment` 매핑 정리
4. `edit/[id]/+page.server.ts:88`에서 빈 문자열을 `undefined`로 정규화

**타입도 어긋난다**: 세미나 _기록_ DB의 `강의 자료`조차 `files` 타입인데 코드는 `{url}`을 쓴다.
`seminar/apply/+page.svelte:84`가 `<input type="url">`이므로 **의도는 링크**다.
첨부를 살리려면 신청 DB에 URL 타입 속성을 새로 만들어야 하고, 그 값이 승인 후
어디로 가는지도 정해야 한다(S-13).

## S-12 🟠 `NOTION_PROPS`가 평면 이름공간이라 두 DB가 충돌한다

```
constants.ts:25  SEMINAR_TITLE:        n("제목")
constants.ts:32  SEMINAR_REQ_TITLE:    n("제목")      ← 같은 문자열
constants.ts:26  SEMINAR_SPEAKER:      n("진행자")
constants.ts:33  SEMINAR_REQ_SPEAKERS: n("진행자")    ← 같은 문자열
```

접두사 규칙이 **두 DB가 별개 속성 어휘를 갖는 것처럼 보이게** 하지만,
신청 DB 6개 키 중 셋이 기록 DB 키와 바이트 단위로 같다.

그래서 `SEMINAR_FILES`가 **어느 쪽에도 안전하지 않은 유일한 예외**라는 사실이 보이지 않았다.
초판이 제안한 "이름을 `SEMINAR_MATERIALS`로 바꾸자"는 증상 처방이다.

**제안**: `NOTION_PROPS.SEMINARS.*` / `NOTION_PROPS.SEMINAR_REQUESTS.*`처럼
**DB 단위로 중첩**한다. 그러면 어떤 상수가 어느 DB 것인지 타입이 강제한다.

## S-4 🟡 학기 정렬이 Notion 옵션 순서에 의존한다 (검증함)

`:24-26`이 `학기`(select) 내림차순으로 정렬한다.

  그 위에 얹은 "속성 혼동과 무관하지 않다"는 서사도 함께 철회한다
- **S-10 `(page as any).created_time`**(`:116`): 페이지 메타 접근 자체는 맞다. 스타일 메모

## 지적하지 않은 것

- **`getSemesterInfo().key` 기본값**(`:48`): 학기를 앱에서 계산하는 것이 맞다. ✅
- **`removeSeminarRequestInNotion = notionArchive`**(`:210`):
  비지적은 유지하되 **초판의 이유는 철회한다.** 초판은 "반려 = 아카이브라는 도메인 의미를
  이름이 표현한다"고 썼는데, 이름은 `remove`/`delete`(`seminars.ts:37` `deleteSeminarRequest`)다.
  **아카이브를 뜻하는 단어가 어디에도 없다.** 오히려 복구 가능한 아카이브를
  "삭제"로 가리는 이름이다. 지적할 만큼은 아니나 이유가 반대였다
- **`(data.speakerIds || [])`**(`:148`): 비지적은 유지하되 **이유 정정.**
  빈 배열은 truthy라 `|| []`가 막지 못한다 — 이건 `null`/`undefined` 가드다.
  그리고 실제로 빈 배열이 올 수 있다(`edit/[id]/+page.server.ts:94-98`).
  의미 있는 관찰은 **쌍둥이 `:190`에는 가드가 아예 없다**는 것이고, 그건 S-6에 넣었다
