# 코드 감사 (Code Audit)

`main` 코드베이스를 파일 단위로 검토하고, 각 검토 결과를 별도 에이전트로 검증하는 작업.

> **성격**: 한시적 작업 문서 디렉터리. `docs/MAINTAINING_DOCS.md`의 taxonomy 바깥이다.
> 감사가 끝나면 이 디렉터리는 삭제하고, 살아남을 내용은 `ARCHITECTURE.md`(구조적 결론),
> `CONTRIBUTING.md`(코딩 규칙), 그리고 실제 리팩터링 커밋으로 옮긴다.

## 무엇을 보는가

| 항목                | 예                                              |
| ------------------- | ----------------------------------------------- |
| 코드 중복           | 같은 로직이 여러 파일에 복사됨                  |
| 하드코딩된 파라미터 | 함수 안에 박힌 매직 넘버·문자열·TTL·URL         |
| 확장 불가 구조      | 항목 추가 시 여러 곳을 함께 고쳐야 하는 설계    |
| clean code 위반     | 책임 혼재, 명명, 함수 길이, 부수효과, 오류 삼킴 |

**데이터·설정 파일은 코드와 기준이 다르다.** 분리해서 다룬다 — [SCOPE.md](./SCOPE.md) A2/A3.

## 절차

파일 하나마다:

1. 파일 전체를 읽고 리뷰 → `files/<상대경로>.md`
2. **검증 에이전트 dispatch** — 지적이 사실인지, 과도하지 않은지, 놓친 게 없는지 냉정하게
3. 에이전트 결과를 **직접 재확인** 후 반영 (에이전트도 틀린다 — 실제로 여러 번 틀렸다)

**한 파일 = 한 문서 = 한 검증.** 묶지 않는다. 묶으면 검증 품질이 떨어진다.
**커밋은 전체 리뷰가 끝난 뒤 한 번에.** 진행 중에는 커밋하지 않는다.

## 판정 기준 (가장 중요)

**기준은 "없어도 동작한다"가 아니라 "논리적으로 불필요하다"이다.**

신장 하나로도 사람은 산다. 그렇다고 신장이 하나인 것이 정상은 아니다.
해부학적으로 둘이 정상이므로 둘을 유지하는 것이 옳다. 코드도 같다.

따라서 **다음은 지적을 감면하는 근거가 될 수 없다**:

| 감면 근거로 쓰면 안 되는 것            | 왜                                                                               |
| -------------------------------------- | -------------------------------------------------------------------------------- |
| "지금 데이터로는 안 터진다"            | 데이터의 성질이지 코드의 성질이 아니다. 데이터는 변한다                          |
| "그 라우트에 도달할 수 없다"           | 도달성은 증상의 크기를 정하지 결함의 유무를 정하지 않는다                        |
| "오염을 일으키는 호출부가 현재 없다"   | **순환 논증.** 좁은 타입의 값어치가 바로 _아직 없는_ 호출부를 막는 것이다        |
| "환경 변수가 없어서 그 경로가 안 돈다" | 배포 환경의 상태다. 설정 하나로 되살아난다                                       |
| "상위 계층이 어차피 막아준다"          | **대체 장기인지 차단기인지 구분할 것.** 프로세스를 죽이는 것은 타임아웃이 아니다 |

반대로 **정당한 감면 근거**는 논리에 관한 것뿐이다 — 인과 주장이 틀렸다,
심각도를 다른 지적에서 빌려왔다, 그 코드가 실제로는 계약을 지키고 있다.

이 구분은 **등급(심각도)에도 적용된다.** 도달성·빈도는 우선순위를 정하는 데는 쓰되,
지적을 🟡로 내리는 근거로는 쓰지 않는다. 우선순위와 등급은 다른 축이다.

## 원칙

- **지적은 근거와 함께.** "복잡하다"가 아니라 "X와 Y가 같은 로직이고, Z를 추가하려면 둘 다 고쳐야 한다"
- **과도한 지적을 경계한다.** 코드 35,522줄짜리 동아리 사이트다. 엔터프라이즈 기준을 들이대지 않는다.
  단, "과도"의 판정도 위 기준을 따른다 — 규모가 작다고 논리적 결함이 결함이 아니게 되지는 않는다
- **동작 변경 제안과 구조 제안을 구분한다.** 전자는 회귀 위험이 있다
- **기준선은 개수가 아니라 목록이다.** 이전 감사는 `svelte-check` 40 errors를 배경 잡음으로
  취급했고, 그 안에 "빌드가 깨져 있다"가 들어 있었다(`pre-migration/CROSS-CUTTING.md` X-1).
  현재 기준선은 실제 출력을 읽고 적었다 — `CROSS-CUTTING.md` XC-1·XC-2

## 지적 ID 규약

파일마다 고유 접두사를 쓴다. **다른 문서와 겹치면 안 된다** —
겹치면 상호참조가 무엇을 가리키는지 문맥으로 추측해야 한다.

| 접두사                                                                                                | 파일                                                                  |
| ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `XC-`                                                                                                 | `CROSS-CUTTING.md` (교차 발견) — **현행**                             |
| `C-`                                                                                                  | **`SCOPE.md`의 사용자 확인 항목** — 별도 이름공간. 코드 지적이 아니다 |
| `X-` `M-` `AC-` `AP-` `S-` `SC-` `U-` `T-` `IX-` `EV-` `N-` `SH-` `SE-` `AG-` `MT-` `AD-` `CA-` `SM-` | **`pre-migration/`에 동결.** 새로 쓰지 않는다                         |

파일별 접두사는 리뷰를 시작할 때 배정하고 이 표에 추가한다.
동결된 접두사와 겹치지 않게 할 것 — 겹치면 상호참조가 어느 시대를 가리키는지 알 수 없다.

> **2026-08-25 정정**: `seminars.md`가 `M-2~M-5`를 써서 `members.md`와 충돌했다 →
> **S-11~S-14**로 변경. `notion.md`(셰임)의 `N-1`·`N-2`가 `client.md`와 충돌했다 →
> **SH-1**·**SH-2**로 변경.
>
> `SCOPE.md`의 `C-1~C-11`은 `client.md`의 `C-1~C-10`과 겹치지만 **바꾸지 않는다** —
> 사용자가 그 번호로 처리 결정을 내렸다(C-1·2·4·5·7 삭제). 인용 시 문서명을 반드시 붙일 것.
