#### ⑥ — 제거 대신 실제 일을 시켰다

`Record<(typeof TABLE_NAMES)[number], any[]>`가 리터럴 누락을 잡아준다고 기대할 수 있지만,
**`scripts/`는 타입체크 프로그램에 없고**(include는 `src/`·`test/`·`tests/`뿐) 실행은 `tsx`가
**타입을 검사 없이 벗긴다.** 즉 그 보장은 어떤 도구도 검증하지 않는 장식이었다.

이 파일의 원칙은 "매칭 실패 항목은 전부 리포트 후 **중단**(조용한 드롭 금지)"인데,
**테이블 자체가 누락되는 경로만 조용했다** — `Object.entries(tables)`로 돌면 9개만 쓰고 끝난다.

그래서 목록을 런타임에서 강제한다: 커버리지 양방향 검사 + 쓰기 루프를 `TABLE_NAMES`에서 순회.
`errors` 게이트가 **업로드 전에** `process.exit(1)`을 하므로 DB를 건드리기 전에 멈춘다.

가드는 `name in tables`가 아니라 `Array.isArray`로 본다 — 키가 `undefined`로 존재하면
누락 검사를 통과하고 쓰기에서 조용히 빠진다. 타입이 검사되지 않는 것이 전제이므로
런타임 검사도 타입을 믿으면 안 된다.

실증(가드 로직만 떼어 실행):

```
정상 10개    : errors [] · 파일 10
1개 누락     : errors ['테이블 누락: studies'] · 파일 9
undefined 키 : errors ['테이블 누락: studies'] · 파일 9
낯선 키 추가 : errors ['알 수 없는 테이블: ghost']
```

- **`build`는 C-17 덕에 이제 가능하다** — 프리렌더가 데이터 계층을 크롤해서
  `SUPABASE_URL` 없이는 실패했다. 시크릿 없는 워크트리에서 통과를 실측했다
- **네 검사 전부에 `if: ${{ !cancelled() }}`** — 한 번의 실행이 **모든 실패를 함께 보고**한다.
  없으면 Lint가 빨간불일 때 타입·빌드 상태가 가려지는데, 감사가 발견한 상태가 정확히 그것이었다

`prettier`는 **여전히 CI 밖**이다 — 추적 파일 131개가 실패 중이라 별도 결정이 필요하다
(한 번 `--write`로 정리 후 투입 / `lint` 스크립트에서 제거해 스크립트와 CI를 일치, 둘 중 하나).

#### P1-2 `(admin)/+layout.server.ts`의 `isMember` 리터럴 ✅ 처리됨

**결정 (2026-09-10): 파일은 남기고 거짓말하는 필드만 제거한다.**

초안은 "파일 삭제"였다 — 검증 에이전트의 제안을 그대로 받은 것이고, 과했다.
닫아야 할 결함은 **`isMember: true` 하나**다.

| 필드       | 루트                                        | (admin) 초안    | 판정                                                                                               |
| ---------- | ------------------------------------------- | --------------- | -------------------------------------------------------------------------------------------------- |
| `isMember` | `!!member && member.status !== "withdrawn"` | `true`          | ❌ **거짓이다.** C-18로 탈퇴 관리자가 존에 들어오는데, 그에게 루트는 `false`를 계산한다 → **제거** |
| `isAdmin`  | `member?.isAdmin === true`                  | `true`          | ✅ 거짓이 아니다. 이 존은 가드가 `isAdmin`을 보장한다 → 유지                                       |
| `session`  | `member ? locals.auth() : null`             | `locals.auth()` | 같은 값. 세션 재해석 1회는 잉여지만 무해 → 유지                                                    |

**파일을 남긴 이유**: 존 레이아웃은 "지금 읽는 코드가 없다"와 별개로 **구조적 자리**다.
관리자 전용 공통 데이터가 생기면 명백한 위치가 거기이고, 존 셋(`(member)`·`(applicant)`·`(admin)`)이
레이아웃을 갖는 대칭도 유지된다.

**남는 잉여는 기록해 둔다** — `isAdmin` 리터럴(`ZA-1` 전반부)과 세션 재해석(`ZA-4`)은
루트와 중복이다. 결함이 아니므로 닫지 않는다.

## 부록 B — 세미나 일정·공개·취소 (2026-09-15)

감사 목록 밖에서 들어온 운영 요청이다. 발단은 한 문장이었다: **“승인을 누른 시점이 세미나
일시로 저장된다.”** 실제로 그랬다 — 승인이 활동·출석 이벤트·전 회원 공지를 한 번에 만들면서
시작 시각을 `승인을 누른 순간`으로 박았고, 그래서 승인된 세미나는 신청이 즉시 닫히고 그날
자정에 만료됐다.

### 스스로 재현해 고친 결함

- **공개 중 취소가 끼어들면** 취소된 세미나에 `active` 출석 이벤트가 남고 전 회원에게 “열립니다”
  메일이 나갔다. 취소의 이벤트 정리가 **아직 만들어지지 않은** 이벤트를 훑고 지나가기 때문이다.
  경합에 기대지 않고 활동 생성 직전에 훅을 걸어 창을 직접 열어 재현했다
  (`publish-cancel-race.test.ts`).
- **취소 권한을 캐시로 판정**했다. 표 읽기는 최대 15초 낡을 수 있어, 관리자가 일정을 과거로 고친
  직후 개설자가 이미 치른 세미나를 취소할 수 있었다. 판정을 전부 쓰기 CAS 안으로 옮겼다.
- **이주로 일정을 잃은 `published` 행**을 “아직 안 열림”으로 읽어, 몇 해 전 세미나가 개설자에게
  취소 가능한 것으로 보였다. `seminarHasStarted` 하나가 서버와 두 화면의 공통 판정이다.
- **취소된 세미나가 개설자 대시보드에 남았다.** 취소는 세미나 행만 뒤집는데 신청 행은 `approved`
  그대로였고, 그 목록만 필터가 없었다.
- **`getPublicGallery`**에 형제 접근자의 상태 필터가 빠져 있었다(호출자 없음 — 그래서 더 위험).
- **손으로 고친 학기가 고정되지 않아** 다음 일정 수정이 덮었다.
- **관리자 취소 버튼의 “이미 시작됨” 판정이 로드 시점 값**이라, 보드를 열어 둔 사이 시작된
  세미나는 409로 거절되고 새로고침 전까지 몇 번을 눌러도 같았다. 판정을 제출 시점으로 옮겼다.
