> **성격**: 한시적 작업 문서. [README](./README.md) 참조.
> 기준일: **2026-09-14**. 브랜치 `chore/code-audit-v2` @ `624ece1`.
>
> `W-1`(루트 레이아웃 스트리밍 → 상태 코드 유실)을 닫은 뒤, **"모든 상태 가능성에 적절한 코드가

## 방법

두 관점의 독립 에이전트를 병렬로 붙이고, 🔴 항목은 **직접 재현**했다.

| 관점      | 범위                                                                                                     |
| --------- | -------------------------------------------------------------------------------------------------------- |
| 렌더 계층 | `hooks.server.ts` · 가드 · 전 `+page.server.ts`/`+layout.server.ts` 로드와 form action · `+error.svelte` |
| API 계층  | `src/routes/api/**` 7개 · `AppError` → HTTP 매핑 · 메서드 불일치 · 스펙 양방향 대조                      |

측정은 `vite dev` + `curl`. 로컬은 `SUPABASE_URL`·`CRON_SECRET` 미설정이라 장애·미설정 분기가 실측 가능했고,
가드를 통과해야 하는 경로는 `DATA_BACKEND=memory` + `?dev_preview=member|admin`으로 열었다.

## 발견 — `HS-1` ~ `HS-13`

접두사 `HS-`(HTTP Status)는 새로 배정했다. 동결된 `SC-`와 겹치지 않게 골랐다.

| ID      | 등급 | 발견                                                                                                                                                                                                                                                                                                                                                             | 현재 → 적절                                          | 검증                                                      | 작업        |
| ------- | ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | --------------------------------------------------------- | ----------- |
| `HS-1`  | 🔴   | **스트리밍 페이지의 액션 실패가 전부 200.** `streamed:`를 쓰는 라우트는 `(public)/+page.server.ts`와 `(admin)/admin/+page.server.ts` 둘뿐인데 그 둘이 **액션 20개**를 갖는다. Kit이 액션 상태를 제대로 잡아 놓고(`page/index.js:86`) 스트리밍 분기에서 버린다(`render.js:661-680`)                                                                               | 200 → `fail()`의 상태                                | **실측** (두 에이전트 + 직접 통제 비교)                   | ✅ **W-21** |
| `HS-2`  | 🔴   | **로드에서 던진 `AppError`가 500이 된다.** `AppError`는 `HttpError`가 아니고, 로드에는 `runAction` 같은 변환기가 없다. `ensureOrganizer`가 던지는 `NOT_FOUND`·`FORBIDDEN`이 전부 500                                                                                                                                                                             | 500 → 404 / 403                                      | **실측**                                                  | ✅ **W-22** |
| `HS-3`  | 🟠   | **가드가 던지는 404/403/500이 캐시 실드를 우회한다.** `cacheShield`는 `resolve()` **후에** 헤더를 붙이는데 `zoneGuard`가 throw하면 그 줄에 닿지 않는다. 리다이렉트 분기는 이미 알고 수동으로 붙였다(`:129` 주석)                                                                                                                                                 | 헤더 없음 → `no-store` 3종                           | **실측** (`/admin` 404에 헤더 없음 / 미매칭 404에는 있음) | **W-23**    |
| `HS-4`  | 🟠   | **미포획 예외가 봉투를 깬다.** 관리자 큐 3종·presign이 장애 시 `{"message":"Internal Error"}`를 낸다 — `restErrorEnvelopeSchema` 밖이라 클라이언트가 파싱하지 못하고 "새로고침 실패"로 뭉갠다                                                                                                                                                                    | `{message}` → `{error:"SERVICE_UNAVAILABLE"}`        | 실측                                                      | ✅ **W-22** |
| `HS-5`  | 🟠   | **관리자 API가 익명에게 403.** 스펙 §1-1은 404(존재 은폐), HTTP 의미는 401. 실제 비용: **만료된 세션과 비관리자가 구분되지 않아** 30초 폴러가 재로그인 유도 없이 같은 문구만 반복한다. 페이지 쪽 `ensureAdmin`은 404를 지키므로 `/api`만 갈라져 있고 그 예외가 문서화돼 있지 않다                                                                                | 403 → **C-19 결정**                                  | 실측                                                      | ✅ **W-24** |
| `HS-6`  | 🟠   | **`WRITE_CONFLICT`가 503.** CAS 소진은 서비스 장애가 아니라 **다른 사용자와의 경합**이다. 503으로 두면 사용자 경합이 5xx 에러율·SLO에 서버 장애로 집계된다 — 이 프로젝트에서 5xx는 크론 경보 축이기도 하다. `API-SPEC` §1-3 자신이 "조건부 쓰기 실패"를 409 계열로 인정한다                                                                                      | 503 → **409** (+`IMPLEMENTATION-SPEC:256` 동시 수정) | 독해                                                      | ✅ **W-25** |
| `HS-7`  | 🟠   | **POST 후 302가 2곳.** RFC 9110 §15.4.3에서 302는 메서드 보존이 규범이라 새로고침·뒤로가기에서 **이벤트 생성 POST가 재전송**될 수 있다. 나머지 4곳은 303이다                                                                                                                                                                                                     | 302 → 303                                            | 독해                                                      | **W-26**    |
| `HS-8`  | 🟠   | **`fail(500, { error: e.message })`가 원시 예외 문자열을 클라이언트에 싣는다.** Postgres·fetch 에러 텍스트가 그대로 나간다. `API-SPEC` §1-2("`error`는 코드")도 위반                                                                                                                                                                                             | `e.message` → `"INTERNAL"`                           | 독해                                                      | **W-27**    |
| `HS-9`  | 🟡   | **크론·헬스의 501.** RFC 9110 §15.6.2의 501은 "메서드 미구현"이다 — 구현돼 있고 값 하나가 빠진 상황이 아니다. 503이 맞다. **그러나 런북(`OPERATOR-TODO.md:147`)이 상태 코드만으로 미설정/불일치를 가른다.** 그리고 `CS-4`(501을 401보다 먼저 반환 → 설정 상태 노출)와 **한 덩어리다** — 따로 고치면 하나가 다른 하나를 무효화한다                                | 501 → **C-20 결정**                                  | 실측                                                      | ✅ **W-28** |
| `HS-10` | 🟡   | **`HEAD`가 GET 핸들러를 실행한다.** Kit `endpoint.js:19`가 `HEAD` export가 없으면 GET으로 넘기고, 크론 3라우트는 `GET`만 export한다. **Bearer를 가진 HEAD 한 번이 만료 처리·회차 생성·스테이징 삭제·주간 백업·heartbeat ping을 전부 실행한다.** 익명은 501/401에 막히지만 safe-method 위반이다 (`CM-3`의 미측정 절반)                                            | GET 실행 → `HEAD` 명시 export                        | **실측 + Kit 소스 확인**                                  | **W-29**    |
| `HS-11` | 🟡   | _(부분 처리: 데이터 계층 실패가 `SERVICE_UNAVAILABLE`→503이 됐다. 남은 것은 `Retry-After`)_ **데이터 계층 장애가 500.** 재시도 가능한 일시 장애이므로 503 + `Retry-After`가 맞다. 저장소 전체에 `Retry-After` 0건. 같은 클래스의 장애인데 쓰기 경합만 503(`HS-6`에서 409로 내릴 예정)이라 코드가 갈려 있다. `+error.svelte`에 503 분기도 없다                    | 500 → 503 + `Retry-After`                            | 실측                                                      | **W-30**    |
| `HS-12` | 🟡   | **의미가 틀린 개별 코드 3종.** ① 비활성 이벤트가 GET 403 / POST 409로 갈린다 — 403은 "당신에게 권한이 없다"인데 실제로는 **누구에게도** 열리지 않는다(410이 맞다) ② `seminar/edit/[id]`가 미존재·비pending·비소유를 전부 302 `/`로 뭉갠다(스펙은 404/409/403) ③ 302/303 혼용 5곳                                                                                 | 개별 교정                                            | 독해                                                      | **W-31**    |
| `HS-13` | 🟡   | _(부분 처리: `SERVICE_UNAVAILABLE`은 연결됐다. 남은 것은 업로드 크기 초과의 413)_ **죽은 상태 코드 2개.** `SERVICE_UNAVAILABLE`은 `API_ERROR_CODES`에만 있고 `ERR`에 없어 **서버가 낼 수 없다**. `upload-validation.ts`의 413은 죽은 모듈에 있다(업로드 크기 초과는 현재 400). 둘 다 필요한 자리가 정확히 있다 — 전자는 `HS-4`/`HS-11`, 후자는 presign 크기 분기 | 연결 또는 삭제                                       | 독해                                                      | **W-32**    |

| `HS-14` | 🟠 | **오류 페이지가 내부 문자열을 그대로 렌더한다.** `+error.svelte:31`이 `page.error?.message`를 출력하는데, `hooks.server.ts`의 `"route without zone"`은 `HttpError`라 프로덕션에서도 지워지지 않는다. `"Not Found"`·`"Event not found"` 같은 영문 원문도 한국어 UI에 그대로 나온다 | 원문 → 상태별 한국어 문구 | 독해 | **W-35** |

### 구조 발견 — 오류 본문이 여덟 종류다

상태 표(`core/errors.ts:19-27`)는 중앙에 있는데 **응답 어댑터가 없어서** 엔드포인트마다 손으로 짓는다.

```
{error:"FORBIDDEN"} · {error:"CRON_SECRET is not configured"} · {error:"Unauthorized"}
{error:"Sync failed"} · {ok:false} · {"message":"Internal Error"}
{success:false, failures:[…]} · text/plain "POST method not allowed"
```

`CROSS-CUTTING.md` `XC-7`이 원인을 이미 짚었다 — `requireAdminAction`이 **폼 액션 전용 `fail()`**을 반환해서
엔드포인트 4곳이 그 반환값을 버리고 `json()`을 손으로 짓는다. → **W-33**(`W-11` 흡수)

## 확인함 — 문제 없는 것

전수임을 보이기 위해 남긴다.

- 훅: 미매칭 404 위임 · `building` 우회 · api/공개 fast-path · **리다이렉트 303 + 수동 `no-store`**(이 저장소에서 유일하게 올바르게 처리된 우회) · `misconfigured` 500 fail-closed
- 가드 `decide()` 12분기 전부 스펙 일치. `(admin)` 404 은폐는 가드 + 11개 로드의 `ensureAdmin({silent:true})` 이중으로 **일관**
- 명시적 `throw error(404)` 4곳 전부 정확. `events/[id]/[type]`의 `pathId`+`attendCode` 이중 매칭 404는 노출 전에 던지는 **순서까지** 맞다
- `login`의 303 + open-redirect 가드(`startsWith("/") && !startsWith("//")`)
- `AppError` DEFAULT_STATUS 7종 중 6종 정확(`WRITE_CONFLICT`만 `HS-6`)
- 검증 실패 400 단일화 — 422가 더 정확한 경우가 있으나 폼 액션에서 400은 표준 관행이고 **100% 일관**되다. 변경 권고하지 않는다
- 메서드 불일치 405 + `Allow` 헤더는 RFC 9110 §15.5.6대로 (본문이 `text/plain`인 것만 `W-33`)
- 크론 부분 실패의 **500은 옳다.** 207 Multi-Status는 WebDAV 전용이고, 2xx라서 외부 스케줄러의 유일한 경보를 끈다. 부분 실패의 표현은 상태가 아니라 본문(`failures[]`)이 맡는 게 맞다
- 액션 전용 파일 21개의 `AppError` → `fail` 변환 · `+error.svelte`의 404/403/500 3분기 · `prerender = false` 3개 존

## JSON 액션 경로는 결함이 아니다

`POST /?/x`에 `Accept: application/json`이면 `{"type":"failure","status":401,…}` 본문에 **HTTP 200**이 붙는다.
이것은 Kit 설계다(`actions.js`의 `action_json`이 실패에 init을 주지 않는다) — 실패 상태는 봉투가 나른다.
따라서 `HS-1`의 영향은 **JS 없는 폼 제출·모니터링·크롤러**에 한정된다.
